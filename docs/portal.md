# The web portal (`ccp.example.com`)

The portal is the browser half of the cloud: your machines, what each one has, and the history of every
snapshot with a diff between any two of them. It is served **by the `ccp-cloud` binary itself**, from the same
origin as the API, and it opens the vault **in the tab** — the account key is derived there from your vault
passphrase and never leaves the browser.

What it shows today (F2-3):

- **Devices**: name, platform, ccp version, last contact, the profiles that machine has, how many snapshots it
  has sent, and its state against the revision the portal published for it (`pending`, `applied`, `partial`,
  `conflict`, `failed`, `superseded`) with the number of paths that differ.
- **Timeline** of one device: every snapshot with its date, label, size, how many files it holds and whether
  its signature checks out.
- **Diff** between any two snapshots, grouped by area (`ccp`, `global`, each profile, each project) and
  filterable by path.

Publishing a revision or restoring from the portal is **not** here yet: that is F3. Today the portal reads.

## How it is built

It is not built. There is no bundler, no npm, no `node_modules` and no generated bundle to keep in sync with
the source: `internal/cloud/portal/web/` holds plain ES modules and one stylesheet, and `go:embed` puts them
inside the binary. Editing the portal is editing those files and rebuilding `ccp-cloud`.

```
internal/cloud/portal/
  portal.go        the handler: security headers, CSP, ETags, SPA fallback
  web/index.html   the only page
  web/app.css
  web/js/crypto.js Argon2id, XChaCha20-Poly1305, HKDF, Ed25519
  web/js/oidc.js   authorization code + PKCE against Keycloak
  web/js/api.js    the /v1 client
  web/js/vault.js  the account key, in memory only
  web/js/model.js  diff, profiles, areas — no DOM, no network
  web/js/app.js    the views
```

That choice is deliberate and it is about the crypto. **Argon2id and XChaCha20-Poly1305 are in no browser**,
so they had to come from somewhere; pulling them from a dependency — with its build, its lockfile and its
supply chain — for the one page that touches the account key was a worse trade than writing them. What
WebCrypto does give (HKDF, SHA-256, HMAC, Ed25519) comes from WebCrypto. And `crypto_test.mjs` runs all of it
under node against vectors generated by the Go code itself, so «the browser opens what `ccp` sealed» is a test
and not a hope:

```bash
go test ./internal/cloud/portal            # needs node on PATH; it skips without it
```

`model_test.mjs` does the same for the diff: the portal's diff is compared against `snapshot.Diff`. Two diffs
that disagree about the same two snapshots are two truths, and nobody would know which to look at.

## Looking at it without deploying anything

```bash
CCP_PORTAL_DEMO=1 go test ./internal/cloud/portal -run Demo -v
```

It prints a URL and a vault passphrase (`demo`), and serves the real portal over a fake API with a **real**
vault: invented machines, snapshots and a published revision. The login is the only thing stubbed out — paste
the line it prints into the browser console and reload. A screen you can only try by deploying is a screen
nobody tries.

## How it is served

`ccp-cloud` mounts the portal at `/`, under the same host as `/v1`. That is what makes the API calls
same-origin: no CORS to negotiate against your own API, and no token in a URL.

| Variable | Default | What it does |
|---|---|---|
| `CCP_CLOUD_PORTAL` | `1` | `0` turns the portal off and leaves the root a plain 404 |
| `CCP_CLOUD_OIDC_PORTAL_CLIENT_ID` | `ccp-portal` | the public Keycloak client the tab logs in with |

The issuer (`CCP_CLOUD_OIDC_ISSUER`) has to be `https` — or `http` against loopback, the same exception the
CLI makes for the test stack. The portal refuses to start otherwise, because the issuer's origin is what goes
into `connect-src`: a portal served with a policy that cannot reach Keycloak is a login screen that fails when
you press the button, and the reason only shows up in the browser console.

Every response carries a **strict CSP** — `default-src 'none'`, `script-src 'self'`, `style-src 'self'`,
`connect-src 'self' <issuer origin>`, `frame-ancestors 'none'`, `base-uri 'none'`, `form-action 'none'` — plus
`nosniff`, `no-referrer`, `X-Frame-Options: DENY` and `Cross-Origin-Opener-Policy: same-origin`. No inline
script, no inline style, no third-party anything. If you ever need one, the policy is the thing to change
first, on purpose: this is the page that holds the account key.

## What Keycloak needs

One public client in the realm, next to `ccp-cli`:

- **Client id** `ccp-portal`, public (no secret — a SPA cannot keep one), standard flow on, direct access
  grants off, service accounts off.
- **PKCE** required, method `S256`.
- **Valid redirect URIs**: `https://ccp.example.com/` — the portal always redirects back to the root and
  routes with the hash.
- **Web origins**: `https://ccp.example.com`. This one is easy to forget and it is the one that breaks the
  login: the code is exchanged with `fetch` against Keycloak's token endpoint, and without the origin the
  browser blocks the response.
- **Valid post logout redirect URIs**: `https://ccp.example.com/`.
- The same `aud: ccp-api` mapper the other clients have, or the API will reject the token.

## What lives in the browser, and where

- **The account key (AK) is in memory only** — never in `localStorage`, never in `sessionStorage`, never sent
  anywhere. Closing the tab forgets it, and so does 15 minutes without touching the page.
- **The session** (access and refresh token) is in `sessionStorage`: it dies with the tab, so a reload does not
  throw you out but closing the window does. The refresh is there because Keycloak's access token lasts five
  minutes and the portal should not fall over halfway through reading a timeline.
- **The device id** is in `localStorage`, per account. The portal registers itself as one more device of the
  account (platform `portal`): the API asks for a device on every authenticated call, and what publishes
  revisions has to be identifiable in the audit like any other machine. It shows up in the device list marked
  as `portal`. Revoking it is enough; the browser will register a new one next time.

## Signatures, and the three answers

A snapshot's signature is checked in the tab against the public key **derived from the account key**, not
against the one the server sent: a compromised server can refuse to serve you, but not forge a snapshot. The
result has three states and the portal paints all three — `firma ✓`, `firma ✗` and `firma ?`. The last one
means *this browser cannot verify Ed25519*, which is not the same as valid; saying «fine» because nobody could
look is exactly what `ccp desktop doctor` is forbidden to do ([ADR 0009](adr/0009-desktop-identity-is-not-durable.md)).
Ed25519 in WebCrypto needs Chrome 137+, Safari 17+ or Firefox 130+.
