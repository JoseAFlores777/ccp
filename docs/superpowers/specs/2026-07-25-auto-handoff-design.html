Resumen ejecutivo

Hard constraint: Cambiar de perfil requiere reiniciar claude. ANTHROPIC_BASE_URL, ANTHROPIC_AUTH_TOKEN, CLAUDE_CONFIG_DIR se leen una sola vez al arrancar. No existe failover multi-provider en Claude Code.

La arquitectura elegida es ccp session: un supervisor en el binario Go que hace fork/exec de claude como hijo, monitorea 3 sensores de límite, y al detectar agotamiento realiza un handoff en-process y re-lanza claude --resume bajo el siguiente perfil. Cero cambios al rc instalado — el subcomando ccp session llega por el fall-through *) command ccp "$@" que ya existe en shellinit.go.

Se evaluaron 4 arquitecturas rivales con crítica adversarial sobre 95 hallazgos verificados en Claude Code 2.1.220 y el código de ccp v2. Se recomienda shippear headless en v1 y gatear interactive en un experimento de 20 minutos (¿StopFailure dispara en límite de suscripción interactivo?).

Señales de detección

SensorProactivoInteractiveHeadlessCalidadNota
statusLine rate_limits ✅ % + epoch ✅ ❌ sin TTY Mejor señal Solo suscripción. refreshInterval configurable.
StopFailure hook ❌ reactivo ⚠️ NO VERIFICADO ✅ Hook correcto ¿Dispara en límite de suscripción interactivo? El proceso no termina el turno.
stream-json api_retry ❌ reactivo N/A ✅ documentado Más limpia error:"rate_limit" + error_status:429.
Transcript tail .error=="rate_limit" ❌ reactivo ✅ ✅ Funciona Turno ya falló cuando se detecta.

Signal gap crítico: 89/89 eventos reales en esta máquina son five_hour en cuentas oficiales OAuth. Interactive no termina el turno — se queda vivo con /rate-limit-options. Si StopFailure no dispara en ese caso, el sensor reactivo interactivo está ciego. Gate para phase 3.

4 arquitecturas evaluadas

🏗️

1. Supervisor — Elegida

ccp session: binario Go hace fork/exec de claude como hijo. Zero cambios al rc. Cero reinstalación. Monitorea 3 sensores en goroutines, mata en turn boundary, handoff en-process, re-exec.

XL headless ✅ interactive ⚠️

📊

2. Budget Scheduler — Graft parcial

Pre-emptive: muestrear .cachedUsageUtilization, armar handoff al 85-95%, frenar en Stop hook. Nunca tocar el límite.

five_hour.utilization lee 0 en caches

🪝

3. Sentinel Relay — Graft parcial

Hooks en cc-home/settings.json detectan límite → sentinel file → _ccp_autocheck actúa en el prompt loop. Sin daemon, peso mínimo.

actuación desde precmd es frágil

🔀

4. Router Proxy — Feature separado

localhost HTTP proxy multiplexa API keys. Failover in-process sin restart. Pero 0/89 límites reales son API-key — todos OAuth.

XL no cubre OAuth

Decisiones y trade-offs

✅ Elegido

Go binary (ccp session)

❌ Descartado

Shell function (_ccp_autocheck)

💡 Por qué

Cron/CI necesita binario. precmd con flock bloqueante + subshells de handoff es frágil.

✅ Elegido

statusLine rate_limits

❌ Descartado

Transcript tail parsing

💡 Por qué

Proactivo > reactivo. resets_at en epoch. Solo suscripción — pero 89/89 límites reales lo son.

✅ Elegido

SIGTERM → handoff → re-exec

❌ Descartado

Hook continue: false

💡 Por qué

Hook no puede cambiar provider. SIGTERM documentado (exit 143, SessionEnd corre).

✅ Elegido

Headless v1, interactive v3

❌ Descartado

Ship interactive sin verificar

💡 Por qué

StopFailure en interactive no está verificado. 20 min de experimento → gate para phase 3.

✅ Elegido

allow_from explícito, default deny

❌ Descartado

Derivar del rules tree

💡 Por qué

Reglas son geográficas (path→profile), no de confianza. work-1→DeepSeek ya pasó manualmente 5×.

✅ Elegido

Lift no-chain con --chain para préstamos

❌ Descartado

Dejar invariante, pagar end→forward

💡 Por qué

Sin lift, round-robin 3 cuentas = 2× RewriteSession (29MB) + 4 sesiones nuevas. Con lift = 1 CopyTranscript por hop.

✅ Elegido

Router proxy: feature independiente

❌ Descartado

Daemon compartido, parte del ladder

💡 Por qué

0/89 límites reales son API-key. Daemon tiene riesgo de puerto/token invalida otras sesiones.

✅ Elegido

--yolo flag per-run, nunca persistido

❌ Descartado

Auto-detectado, guardado en yaml

💡 Por qué

Unattended permission skip es peligroso. Usuario debe pedirlo explícitamente cada vez.

Plan de ejecución por fases

Fase 1: ccp session headless

2–3 semanas · v1 shippeable

Comando: ccp session -p [--policy <name>] [--max-hops N] [--yolo] [--session-id <uuid>] [-- <claude args>]

Archivos nuevos:

  • internal/cli/session.go — dispatch, flags
  • internal/supervisor/supervisor.go — loop: launch → watch → handoff → relaunch
  • internal/supervisor/detect.go — stream-json api_retry parser + exit code
  • internal/supervisor/policy.go — carga auto_handoff de ccp.yaml
  • internal/core/auto.go — AutoConfig struct, load/save, defaults

Sin cambios a: shellinit.go, bash oracle, golden gate, parity test.

Tests: loop sintético con fake claude bin + integración handoff_store real en tmp home.

Fase 2: Detección por hooks + monitoreo

1–2 semanas · experimento crítico

Comandos: ccp auto install, ccp auto status [--json], ccp auto test --profile <n>

Archivos: internal/cli/auto.go, internal/core/autohooks.go (fragmento gestionado de settings.json, merge en CfgRegenerate)

Experimento crítico: Agotar cuenta interactivamente, verificar si StopFailure dispara. Si no: notificación sin actuación automática.

Fase 3: Interactive + lift invariantes

2–3 semanas · gated en experimento fase 2

Features: ccp session sin -p hereda TTY, statusLine sensor proactivo, StopFailure backstop, lift invariante no-chain con --chain, ccp handoff prune --keep N, ccp handoff sessions [--json] público.

Archivos: internal/supervisor/tty.go, internal/core/handoff.go (HandoffHop), internal/cli/handoff_prune.go

Fase 4: Router proxy (feature independiente)

2–3 semanas · API-key pool

Comando: ccp pool run [--pool <name>] [-- <claude args>]

Per-session foreground child. Sin daemon. Pool de API keys con failover in-process (mismo proveedor, distintas keys + model name mapping).

Archivos: internal/router/server.go, pool.go, rewrite.go, classify.go
