ccp_

Una cuenta de Claude Code distinta en cada carpeta. En tu repo de trabajo, tu cuenta de empresa; en tu proyecto personal, tu cuenta personal; en tus experimentos, DeepSeek. El cambio ocurre solo, con hacer cd.

// oficial

Cuenta Anthropic

Tu login de empresa o personal, cada uno aislado.

// proveedor

DeepSeek & cía

Un endpoint compatible con su propia API key.

// default

Tu login normal

Tu ~/.claude de siempre. Sin reglas, gana este.

macOS · Linux bash · zsh requiere Claude Code + git

§ 00Empieza aquí

El modelo mental — 30 segundos

  1. Un perfil es una identidad: una cuenta oficial de Anthropic, un proveedor tipo DeepSeek, o tu login normal (default).
  2. Una regla dice "esta carpeta (y sus subcarpetas) usa tal perfil".
  3. Gana la regla más específica. Sin regla → tu login normal.

Cuando entras a una carpeta, ccp aplica el perfil correcto en esa terminal mediante un hook. Luego corres claude normal.

Pruébalo · ¿qué perfil gana?
cd

resuelve a

¿por qué "la más profunda"?

Las reglas anidan. ~/work cubre todo lo de adentro, pero si una subcarpeta tiene su propia regla, esa es más específica y manda solo ahí. Así puedes tener una excepción puntual sin tocar la regla del padre. Eso es el carve-out del Caso 04.

Herencia de config — Claude ↔ perfiles

Cada perfil es un CLAUDE_CONFIG_DIR aislado que hereda de tu config global de Claude. Tu ~/.claude es la raíz; el perfil default la usa tal cual, los perfiles con nombre la extienden con un overlay. Haz clic en un nodo.

·Una sola vez

Instalación

Cinco pasos. Cópialos en orden.

01

Instala el binario. Una línea, sin clonar nada.

curl -fsSL https://raw.githubusercontent.com/JoseAFlores777/ccp/main/install.sh | bash
¿qué hace esa línea?

Descarga el binario prebuilt de tu OS/arch desde el GitHub Release y verifica su sha256 contra el checksums.txt del release — si no cuadra, aborta. Después copia el repo en ~/.config/ccp/src (clon superficial, o un tarball si no tienes git): de ahí salen los comandos /ccp: y eso es lo que ccp upgrade re-ejecuta luego.

¿Prefieres leerlo antes? curl -fsSL …/install.sh -o install.sh, lo lees, y luego bash install.sh. Desde un clon es el mismo script: git clone https://github.com/JoseAFlores777/ccp.git && cd ccp && ./install.sh.

02

~/.local/bin en tu PATH. Solo si el paso 1 te advirtió, añade a ~/.zshrc o ~/.bashrc:

export PATH="$HOME/.local/bin:$PATH"
¿qué es el PATH?

La lista de carpetas donde tu shell busca comandos. Si ccp no está ahí, el shell no lo encuentra y verás command not found.

03

Instala la función de shell y el hook automático.

ccp install
¿por qué hace falta una función?

El binario corre en un proceso hijo y no puede cambiar el entorno de tu terminal. La función de shell sí: por eso ccp install la agrega a tu rc, y ella aplica el perfil con export.

04

Recarga tu shell — usa el archivo de TU shell.

source ~/.zshrc     # zsh
source ~/.bashrc    # bash
05

Confirma que quedó bien.

ccp doctor

Si ves "Función 'ccp' cargada", estás listo.

§ 01El más común

Tu cuenta de trabajo en tu carpeta de trabajo

El flujo base. Los demás casos son variaciones de este.

01

Crea el perfil oficial "work".

ccp profile add work --official
02

Inicia sesión en ese perfil (una sola vez).

ccp profile login work

Dentro de Claude Code: escribe /login, autentícate con tu cuenta de trabajo, y sal con /quit.

03

Dile a ccp qué carpeta usa "work".

ccp path set ~/work work
04

Pruébalo: entra y abre Claude.

cd ~/work && claude

Arranca con tu cuenta de trabajo. No tuviste que hacer nada más.

§ 02Otra identidad

Añadir tu cuenta personal

Igual que el caso 1, con otro nombre y otra carpeta.

01

Crea el perfil.

ccp profile add personal --official
02

Inicia sesión (una vez), con tu cuenta personal.

ccp profile login personal

Dentro: /login con tu cuenta personal, luego /quit.

03

Asigna tu carpeta personal.

ccp path set ~/personal personal

~/work sigue siendo trabajo; ~/personal ahora es personal.

§ 03Proveedor

Una carpeta con un proveedor (DeepSeek / Kimi / GLM)

Para experimentos o trabajo donde prefieras un proveedor compatible en vez de tu cuenta Anthropic. Hay presets built-in para DeepSeek, Kimi (Moonshot) y GLM (Z.ai).

01

Crea el perfil de proveedor — elige el preset.

ccp profile add deepseek --deepseek   # DeepSeek
ccp profile add kimi     --kimi       # Kimi (Moonshot)
ccp profile add glm      --glm        # GLM (Z.ai)

Cada preset rellena el ANTHROPIC_BASE_URL correcto, los modelos por defecto y las vars de tuning recomendadas por el proveedor (Kimi: ENABLE_TOOL_SEARCH, CLAUDE_CODE_AUTO_COMPACT_WINDOW; GLM: API_TIMEOUT_MS, CLAUDE_CODE_AUTO_COMPACT_WINDOW). Sobreescribe cualquier campo con --base-url --pro --flash --effort.

02

Guarda tu API key de DeepSeek (te la pide oculta).

ccp key deepseek
¿dónde queda la key?

En ~/.config/ccp/profiles/deepseek/api_key con permisos 600. Nunca va al YAML, ni al rc, ni a git.

03

Asigna la carpeta.

ccp path set ~/labs deepseek
04

Úsalo.

cd ~/labs && claude
§ 04Excepción

Sacar una subcarpeta de su regla (carve-out)

Tu ~/work usa la cuenta de trabajo, pero hay un cliente puntual donde quieres tu login normal.

Un solo paso — asigna esa subcarpeta al perfil default.

ccp path set ~/work/cliente-x default
Por qué funciona~/work sigue en "work", pero ~/work/cliente-x usa tu login normal. La subcarpeta más específica siempre manda. ¿Quieres verlo? Vuelve al playground del modelo mental y escribe ~/work/cliente-x.

Cambiar a mano en una terminal

Volver a tu login normal:

§ 07Migración

Vengo de dsctl (la versión vieja)

ccp reemplaza a dsctl. La migración es automática.

01

La primera vez que corras ccp, migra solo: crea un perfil deepseek con tu config vieja y convierte tus reglas. Solo úsalo:

ccp status
02

Quita el bloque viejo de dsctl de tu shell.

dsctl uninstall

Tus reglas viejas quedan respaldadas en ~/.config/ccp/rules.dsctl.bak.

·Avanzado · Sin perder contexto

Handoff — continuar una sesión bajo otro perfil

Cuando un perfil se queda sin tokens/cuota a media conversación, sigue la misma sesión con otro perfil sin perder el contexto.

Un proceso claude vivo congela sus credenciales al arrancar, así que ccp use no puede hot-swapearlas. ccp handoff hace lo único limpio: persiste el contexto → cambia de perfil → reanuda la misma conversación en un proceso nuevo con los tokens del perfil destino.

El flujo completo — interactivo o por flags.

ccp handoff                       # TUI: elige perfil destino → sesión → confirma
ccp handoff <to>                  # salta el picker de perfil
ccp handoff <to> --session <uuid> # salta ambos pickers (scriptable)
ccp handoff resume [<uuid>]      # vuelve a entrar a un handoff vivo, sin cerrarlo
ccp handoff end [<uuid>]         # trae el contexto de vuelta al origen y reanuda ahí
ccp handoff status [--all]        # qué hay en vuelo aquí (o en todos lados)
ccp handoff list                 # historial (archivados) + activos

Puedes tener varios handoffs en vuelo a la vez — uno por sesión, en tantos repos como quieras. ccp handoff sin argumentos abre el panel gestor: enter reanudar · e terminar · n nuevo · y toggle skip-permissions · q salir.

Mantenimiento. discard suelta un marcador cuyo transcript ya no existe; prune recorta el historial archivado (una entrada por handoff cerrado, y nada las quitaba nunca).

ccp handoff discard [<uuid>]     # archiva un marcador SIN traer nada de vuelta
ccp handoff prune --keep 20      # por defecto 50 · --keep 0 lo vacía
ccp handoff sessions --json      # las sesiones de este directorio (datos del picker)

prune y sessions son más nuevos que la función de shell que quizá tengas instalada: si ves un error diciendo que se reenviaron como perfil destino, corre ccp install y abre una terminal nueva.

El modelo mental Pides prestados los tokens de otro perfil para una sesión, y devuelves el trabajo al volver. handoff end hace back-sync del contexto actualizado al perfil origen como sesión nueva (no destructivo); la sesión de vuelta muestra [de <perfil>] en su título.
Encadenar a mano sigue rechazado (A → B → C sobre la misma sesión — termina esa con end primero), y también prestar una sesión a dos perfiles a la vez; el supervisor de auto-handoff sí encadena, pero sin apilar niveles. status, list y discard funcionan en cualquier lado; los comandos que reanudan la sesión corren a través de la función shell de ccp, así que ccp install debe estar activo.
·Avanzado · Desatendido · Runbook

Auto-handoff — rotar de perfil solo

ccp handoff es la respuesta manual a "esta cuenta se acabó". ccp session es la automática: corre claude como proceso hijo, vigila el límite de uso, presta la sesión a otro perfil y la relanza ahí. Sigue los seis pasos en orden — cada uno se puede verificar antes de pasar al siguiente.

Por qué hace falta un supervisorUn claude vivo no puede cambiar de perfil: ANTHROPIC_BASE_URL, ANTHROPIC_AUTH_TOKEN y CLAUDE_CONFIG_DIR se leen una sola vez al arrancar. Así que lo único limpio es un proceso de fuera que pueda matarlo y volver a arrancarlo en otro lado. ccp session llega al binario por la rama *) command ccp "$@" que la función de shell ya tiene — no hace falta refrescar ccp install para usarlo.

El runbook

00

Preflight. Cada perfil que quieras en la cadena tiene que servir por su cuenta, y este directorio necesita una regla de ruta.

ccp doctor                    # logins, keys, función de shell
ccp resolve .                 # ← este es tu PRIMARIO
ccp path set . personal-1     # solo si resolve imprimió "default"

El primario es lo que devuelva ccp resolve $PWD — el dueño natural del directorio. Todo lo demás en la cadena es un préstamo temporal. Si el primario es default, el paso 03 te enseñará una cadena vacía (mira el aviso de ahí).

01

Siembra el bloque de política en ccp.yaml, a partir de tus perfiles.

ccp auto init          # --force sobrescribe un bloque existente

Es aditivo: ccp.yaml se queda en schema version: 2, así que un binario viejo conserva las claves nuevas en vez de rechazar el archivo. Después edítalo a mano — la forma completa está más abajo.

02

Instala los sensores en los perfiles que van a participar.

ccp auto install                  # todos los perfiles no-default
ccp auto install personal-1 work-2   # o solo estos
ccp auto uninstall work-2         # totalmente reversible
¿qué escribe exactamente?

Los dos sensores in-process solo se pueden encender desde cc-home/settings.json, y ese archivo es generado (global ⊕ overlay). Así que auto install añade el perfil a auto_handoff.hooks y regenera como global ⊕ overlay ⊕ capa auto:

· hooks.StopFailure → ccp _limit-hook

· statusLine → ccp _statusline -- <tu statusLine original> — la tuya se envuelve, no se reemplaza: sigue pintando tu barra, ccp solo muestrea el stdin que le llega.

Si no tenías statusLine propia, ccp pinta una mínima en su lugar — el perfil más las dos ventanas de uso, cada una con su medidor y su cuenta atrás hasta el reset: work-1 5h ▏█░░░░░░░░░▏ 2% ·2h13m 7d ▏██████░░░░▏ 59% ·3d. Las dos, porque las dos se vigilan por separado (el salto lo dispara la primera que cruce el threshold) y un porcentaje suelto no diría si te quedan horas o días.

El medidor va verde por debajo del 70%, ámbar entre 70 y 89, y rojo del 90 en adelante — el rojo empieza exactamente en el default de threshold, así que la barra y el motor nunca cuentan historias distintas. Con NO_COLOR se va el tinte y el medidor se sigue leyendo.

Tres cosas que la barra se calla a propósito. Una ventana sin dato se omite, no se pinta como 0%. Un resets_at que ya pasó no produce cuenta atrás: un dato caducado no puede afirmar que tu cuota volvió. Y los días redondean hacia arriba — ·3d cuando faltan 2d23h, nunca ·2d, porque lo único que una cuenta atrás no puede hacer es prometer que la cuota vuelve antes de lo que va a volver.

La línea se dimensiona sola: ccp la monta a tres niveles de detalle, los mide y pinta el más ancho que quepa. Un nombre de perfil largo cuesta celdas de medidor, no corrección — y si no cabe ninguno, recibes la forma compacta sin recortar, porque lo primero que se comería el recorte es el nombre del perfil.

Cualquier hook StopFailure que ya tuvieras se conserva junto al nuestro. Tu overlay no se modifica nunca: la fuente de verdad de "quién tiene los sensores" es auto_handoff.hooks en ccp.yaml, no el archivo generado.

La capa graba la ruta absoluta del binario ccp. Si lo mueves sin correr ccp upgrade (o auto install / profile sync), los sensores se quedan apuntando a la ruta vieja.

03

Verifica el cableado y la cadena resuelta — antes de que algo largo dependa de ello.

ccp auto test --profile personal-1   # payload sintético → camino de detección
ccp auto status                       # política, sensores, muestras, cooldowns
ccp session --dry-run                 # la cadena que USARÍA, y qué se denegó

ccp auto status --json emite enabled, cwd, policy, primary, fallback, denied y sensors (los arrays nunca son null), más error cuando la política no resuelve — el JSON sigue siendo válido y el exit code es 1.

El tropiezo que tendrás primeroccp auto init siembra allow_from con una entrada por perfil con nombre, y default nunca es una de ellas. En un directorio sin regla de ruta el primario es default, así que la cadena entera sale denegada: chain: (empty) con todo bajo denegados. ccp session corre igual — simplemente no tiene a dónde saltar cuando llegue el límite. Arréglalo con una regla (ccp path set . <perfil>) o añadiendo una entrada default: a allow_from.
04

Córrelo. El interactivo hereda tu terminal; el headless entra en un script donde antes iba claude -p ….

ccp session                        # interactivo, claude bajo el supervisor
ccp session -p --policy overnight --yolo -- "refactoriza el parser"

Flags útiles: --max-hops N · --session <uuid> (reanuda una concreta) · --no-return (sin vuelta a casa a media sesión) · --claude-bin <ruta> · --yolo (--dangerously-skip-permissions, prácticamente obligatorio desatendido, nunca se persiste). Todo lo que va después de -- le llega a claude tal cual; un --resume/--session-id/-p/--output-format que pases tú nunca se duplica.

05

Lee el resultado. El código de salida es toda la tabla de triaje.

ExitQué significaQué hacer
0el hijo terminó por su cuentanada — cualquier préstamo abierto se cerró y la conversación está de vuelta en el primario
1error de uso o de configrelee el mensaje: casi siempre enabled: false, un --policy desconocido, o no hay cadena
2fallo de E/S del handoffrevisa disco/permisos en ~/.config/ccp; el marcador está intacto
75todos los perfiles agotados (EX_TEMPFAIL)reintenta luego — la tabla impresa dice cuándo se libera cada uno; el marcador se deja vivo, no se pierde nada
otroel exit code del propio claudetrátalo igual que si viniera de claude (130 = Ctrl-C: nunca rota, el préstamo queda abierto y se te dice)
06

Desatendido. En cron, guarda stdout: es el registro de lo que pasó.

cd ~/repo && ccp session -p --policy overnight --yolo \
  -- "corre el batch de migración" >> ~/logs/ccp-session.log 2>&1
# exit 75 = no pasó nada malo: todas las cuentas están en cooldown. Reintenta.

La traza (saltos, vuelta a casa, tabla de cooldowns) va a stdout porque es la salida del comando. La cháchara operativa (▶ lanzando…, "esperando min_dwell") va a stderr, para que en headless stdout siga siendo parseable — ahí lleva el stream-json del hijo tal cual.

El ciclo: primario → préstamo → vuelta al primario

El supervisor es un péndulo, no un round-robin: sale cuando el primario se agota y vuelve en cuanto la ventana del primario se reabre, aunque queden préstamos frescos. Trabajar horas en la cuenta equivocada es peor que esperar.

La vuelta a casa no es un handoff al revés: es handoff end, que hace back-sync de la conversación al primario como sesión nueva con uuid nuevo (no destructivo — el transcript viejo se queda donde está). El supervisor imprime ese uuid: es el que le pasarías a claude --resume para seguir a mano.

max_hops cuenta préstamos, no movimientosVolver a casa es cerrar un préstamo, así que ni gasta presupuesto ni lo bloquea uno agotado — si no, max_hops: 6 significaría "tres viajes de ida y vuelta", y un presupuesto gastado dejaría la conversación varada en la cuenta de otro con el primario libre. Sigue siendo un tope anti-bucle duro: toda vuelta a casa tiene que venir precedida de un préstamo, y ese sí paga, así que una corrida nunca hace más de 2 × max_hops + 1 lanzamientos.
el temporizador return_check — no es un reloj pasivo

Mientras la sesión está prestada, un temporizador pregunta solo, cada return_check minutos, si la ventana del primario se reabrió. Nadie tiene que topar un límite para que vuelvas a casa — y ese es el punto: ningún sensor dispara cuando se libera otra cuenta, así que sin el temporizador una corrida pasaría la noche en el préstamo después de que la ventana de 5h del primario se reabriera a las 3am.

Solo se arma mientras la sesión está en un préstamo real (marcador vivo cuyo origen es el primario), con --no-return apagado y return_check > 0. Cada decisión es barata — unas comparaciones y un stat del transcript. Lo que no es barato es el desenlace: su única acción es mandarle SIGTERM al claude vivo (10s de gracia para vaciar su .jsonl y correr sus hooks SessionEnd), cerrar el préstamo y relanzar con el uuid nuevo. Un proceso muerto y un hijo nuevo, no una comparación de timestamps.

De ahí las cuatro condiciones que exige, todas: préstamo vivo · cooldown del primario vencido · min_dwell ya cumplido aquí · sesión ociosa durante return_idle. Un evento de límite ya encolado por un sensor también le gana (rotar en su lugar conserva el cooldown del perfil que se deja). Si falta cualquiera, espera y vuelve a preguntar al periodo siguiente — nunca fuerza el movimiento.

El perfil que dejas no se marca agotado: lo dejaste voluntariamente, conserva su crédito.

La vuelta a casa espera al silencio (return_idle, 90s)Es el único movimiento que el supervisor hace por razones propias: rotar por un límite mata a un hijo que ya no puede trabajar (su cuenta responde 429), pero volver a casa mataría a uno que funciona bien. Solo con los defaults (min_dwell: 20m + return_check: 10m) cualquier préstamo de más de veinte minutos terminaría en el instante en que venciera el cooldown del primario — contigo tecleando, a mitad de un turno o con una tool call en vuelo, y una tool call interrumpida la re-ejecuta --resume y puede no ser idempotente. Por eso el transcript no puede haber sido tocado en return_idle. Un transcript que no existe no está ocioso (no sabemos nada, y matar por ignorancia es justo lo que se evita); return_idle: 0s es el opt-out explícito. Perder una oportunidad de volver es barato; quitarte la terminal a media frase no.
min_dwell no vale igual para todos los sensoresSe aplica entero solo al sensor proactivo — el que muestrea el consumo y avisa antes de que nada haya fallado. Ahí esperar sale gratis y evita que un pico queme la cadena. Un evento reactivo es la situación contraria: el turno ya falló, el 429 está servido y estás mirando un error. Como el reloj del dwell arranca con la corrida, el valor entero te dejaría hasta veinte minutos dentro de una cuenta muerta teniendo otra fresca al lado. Así que los reactivos (transcript, stream-json, hook) rotan tras un piso corto de 30s, que sigue evitando que tres perfiles se quemen en un minuto. Un origen que no sepamos reconocer cae del lado urgente a propósito: rotar un poco antes es mejor que retenerte dentro de un límite. La vuelta a casa de arriba es la excepción y exige el valor completo.

Cómo leer el contador. Un movimiento de ida es préstamo N/6 (el préstamo N de tus max_hops); una vuelta a casa es vuelta a casa, no gasta préstamo: siguen N/6. El número no sube al volver, y la línea lo dice en voz alta en vez de dejarte adivinando por qué dos movimientos seguidos muestran 1/6. A la vuelta a casa nunca se le llama préstamo, la haya causado lo que la haya causado.

La política (auto_handoff en ccp.yaml)

auto_handoff:
  enabled: true              # interruptor maestro: false = ccp session se niega a correr
  hooks: [personal-1, work-2]    # perfiles con la capa de sensores instalada
                                 # (la gestiona `ccp auto install/uninstall`)
  policies:
    default:
      # Préstamos, en orden de preferencia. El primario es IMPLÍCITO (ccp resolve $PWD)
      # y se descarta en silencio si lo listas aquí.
      fallback: [work-2, personal-deepseek]
      threshold: 90          # % de la ventana de uso que dispara un salto proactivo
      min_dwell: 20m         # tiempo mínimo antes de rotar (entero solo para el sensor proactivo)
      max_hops: 6            # tope duro de PRÉSTAMOS por corrida (volver es gratis)
      return_check: 10m      # cada cuánto reconsiderar el primario estando prestado
      return_idle: 90s       # …y cuánto debe llevar la sesión EN SILENCIO
      cooldown:
        strategy: resets_at  # usa el resets_at que reporta la API (suscripciones)
        fallback: 1h         # …o esta espera fija cuando no hay resets_at

    overnight:               # `ccp session -p --policy overnight`
      fallback: [personal-1, work-2]
      threshold: 85
      max_hops: 12

    work:
      fallback: []           # sin préstamos: si el primario muere, la corrida para

  allow_from:                # verja de cumplimiento
    work-1: [work-1]                                   # nunca rota
    work-2: [work-2, personal-1]
    personal-1: [personal-1, work-2, personal-deepseek]

La verja allow_from

Rotar solo, a las 3am, sin nadie mirando, significa que la conversación de un cliente podría acabar en una cuenta personal — o en la API de un proveedor externo. Las reglas de ruta son geográficas (qué carpeta es de quién), no una declaración de confianza, así que la verja va aparte y explícita.

allow_fromEfecto
ausente o vacíosin verja — se permite toda la cadena fallback
declarado, con entrada para el primariosolo se permiten los perfiles de esa entrada; el resto salen como denegados
declarado, sin entrada para el primariodeny total — ningún préstamo

Esa última fila es el punto: declarar el mapa es declarar la intención de gobernar los préstamos, así que un perfil que se te olvidó añadir se queda quieto en vez de heredar barra libre. ccp session --dry-run y ccp auto status imprimen los dos qué se denegó y por qué.

Editar la cadena — añadir, reordenar o quitar un préstamo

ccp auto chain                        # la cadena EFECTIVA de este directorio
ccp auto chain add personal-deepseek  # lo añade al final, y autoriza el préstamo
ccp auto chain add work-2 --at 1      # lo inserta en una posición (1-based)
ccp auto chain mv work-2 2            # reordena — el orden ES la preferencia
ccp auto chain rm personal-deepseek   # lo saca, y retira la autorización
ccp auto chain set work-1,work-2      # reemplaza la cadena entera

Todos aceptan --policy <nombre> (por defecto: default) y actúan sobre el primario del directorio actual, que es el único cuya entrada de allow_from pueden tocar.

add escribe dos claves, y eso es justo el punto. Quien escribe «añádelo a la cadena» quiere que el perfil se use, y un fallback sin su allow_from no se usa jamás, en silencio. Dejar las dos claves separadas en la CLI reproduciría la trampa que el yaml ya tiende. Pero allow_from es un gate de cumplimiento y puede estar puesto a propósito, así que el ensanche va con tres límites duros: toca solo la entrada del primario actual, imprime exactamente qué cambió en cada clave por separado (+nombre autoriza, -nombre retira), y --no-allow lo desactiva.

rm —y los perfiles que set deja fuera— va en la dirección contraria y retira la autorización, otra vez solo de esa entrada. Eso es lo que hace reversible a add: sin ello el gate solo podría crecer, y deshacer un add equivocado exigiría editar el yaml a mano, que es justo lo que estos comandos vienen a evitar.

Toda mutación cierra releyendo la cadena efectiva del disco, así que ves lo que va a ver el motor — incluido lo que allow_from siga bloqueando.

Lo que quieresComando
Añadir un préstamoccp auto chain add <perfil> — escribe fallback y allow_from[<primario>]
Cambiar el orden de preferenciaccp auto chain mv <perfil> <pos> — el orden es la preferencia
Quitar un préstamoccp auto chain rm <perfil> — retira también la autorización (--no-allow la conserva)
Dejar de rotar en un directorioccp auto chain rm de cada préstamo, o dale a ese primario una política con fallback: []
Otra cadena para otro trabajoañade otra política bajo policies: y usa --policy <nombre>
El único comando que te saca de un deny totalEn un directorio cuyo primario no tiene entrada en allow_from, ccp auto chain show dice cadena (ninguno) mientras todos los perfiles están ya dentro de fallback — es lo que siembra ccp auto init. ccp auto chain add <perfil> lo resuelve: un perfil que ya está en la cadena pero al que el gate cierra el paso no es un duplicado, así que se crea la entrada, se avisa de que la cadena en sí no cambió, y el repo empieza a rotar.

Editar el archivo a mano sigue siendo perfectamente válido, y es como se añade una política nueva entera. ccp reescribe ~/.config/ccp/ccp.yaml de forma atómica conservando tus comentarios y cualquier clave que no conozca, así que una anotación sobre por qué un perfil está en la lista sobrevive a cada ccp path set, profile add o auto install posterior.

auto_handoff:
  policies:
    default:
      # El orden ES la preferencia: primero work-2, el proveedor solo como último recurso.
      fallback: [work-2, personal-deepseek]
  allow_from:
    personal-1: [personal-1, work-2, personal-deepseek]   # ← la entrada del primario

Lo que el resolver le hace a fallback, en una sola pasada: el primario es implícito y se descarta en silencio si lo listas · los duplicados se eliminan (no compran un préstamo extra) · default es un destino legítimo (tu login normal de ~/.claude) · el orden que escribiste se respeta tal cual.

Después, los dos pasos de verificación — estar en la cadena no es lo mismo que tener detección.

ccp auto install personal-deepseek   # sensores para el perfil recién añadido
ccp session --dry-run                # a qué resuelve la cadena, aquí

¿Editaste fallback y olvidaste allow_from? --dry-run te lo dice en vez de no hacer nada en silencio. Es el error más común de largo:

Y un nombre que no existe es un error duro, no un salto silencioso. Un typo — o un perfil que borraste — detiene ccp session antes de lanzar nada, con exit 1:

profile rename / profile rm no tocan auto_handoffMueven tus reglas de ruta y tus marcadores de handoff, pero la política de rotación se queda exactamente como estaba — así que renombrar o borrar un perfil que está en una cadena deja un nombre colgando, y el siguiente ccp session en ese directorio falla con el error de arriba hasta que arregles el YAML. Tres sitios llevan nombres de perfil: policies.*.fallback, allow_from (tanto las claves como las listas) y hooks. Busca el nombre viejo antes de cerrar el archivo.
auto init --force empieza de ceroRegenera el bloque desde cero, descartando tus ediciones a mano y tus comentarios. Úsalo para volver a empezar, no para refrescar — el ccp auto init pelado es idempotente y no hace nada si ya hay bloque. Ojo también a que auto init deja a propósito los perfiles de proveedor (DeepSeek/Kimi/GLM) fuera del allow_from sembrado de todos los demás perfiles: mandar una conversación a una API de terceros es justo la decisión que la verja existe para hacer explícita, así que añadir uno a una cadena siempre es un acto manual.

Los sensores — tres a la vez, cuatro en total

Tres corren a la vez en cada modo, porque ninguno lo cubre todo. La redundancia es deliberada: detectar el mismo límite dos veces es gratis (el supervisor deduplica por contenido), estar ciego no.

SensorQué lee¿Proactivo?Inter.Headless

Interactivo corre statusLine + transcript + sentinel; headless corre stream-json + transcript + sentinel. Solo el sensor de statusLine es proactivo, y es justo el que no funciona en headless — por eso el camino headless se apoya en el (muy limpio) evento api_retry.

⚠️ Sin verificar empíricamenteSi el hook StopFailure dispara siquiera en interactivo con un límite de suscripción (ahí Claude Code no termina el turno — ofrece /rate-limit-options). Si no dispara, la detección interactiva descansa en el porcentaje de la statusLine más la cola del transcript. ccp auto test verifica el cableado, no el comportamiento de Claude Code.

Cuando algo se ve raro

+--dry-run dice chain: (empty)

El primario no tiene entrada en allow_from — casi siempre porque es default (aquí no hay regla de ruta). Pon una regla con ccp path set . <perfil> o añade una entrada default:.

+Sale con 75 de inmediato

Todos los perfiles de la cadena están en cooldown. La tabla impresa dice cuándo se libera cada uno. No se perdió nada: el marcador se deja vivo.

+Nunca vuelve a casa solo

Tienen que darse cuatro condiciones a la vez: préstamo vivo, cooldown del primario vencido, min_dwell cumplido y sesión ociosa durante return_idle. Una sesión en la que sigues tecleando no está ociosa — volverás cuando pares, cuando el hijo salga, o en el siguiente límite. Revisa también --no-return y return_check: 0s.

+Desapareció la barra de estado tras auto install

No debería: tu statusLine se envuelve, no se reemplaza. Mira cc-home/settings.json — si el comando envuelto apunta a un binario viejo, corre ccp profile sync (o ccp upgrade).

+Rotó sin que nada detectara un límite

El sensor proactivo de statusLine dispara al threshold % antes de que falle un turno. Sube threshold si quieres que espere más, o lee ccp auto status para ver la última muestra que tomó.

+Una tool call se ejecutó dos veces

Un salto es un SIGTERM en frontera de turno, así que una tool call interrumpida la re-ejecuta --resume y puede no ser idempotente. Es inherente al mecanismo; min_dwell y return_idle existen para que sea raro.

·Avanzado · Escritorio

Claude Desktop — una ventana por perfil

La app de escritorio guarda una sola sesión a la vez. ccp desktop le da a cada perfil su propia instancia: cuenta, servidores MCP, entorno Cowork… y el Code tab. Trabajo y personal, abiertas en paralelo.

Abrir la ventana de un perfil.

ccp desktop open work-1

Sin nombre, ccp desktop open usa el perfil que resuelva la carpeta actual — el mismo resolutor que el hook del prompt, así que la ventana y la terminal nunca acaban en cuentas distintas.

Ver qué haría, sin lanzar ni tocar nada.

ccp desktop open work-1 --dry-run

Imprime el plan y lo que convertiría en el cc-home. Es la forma recomendada de estrenar el comando sobre un perfil que ya usas.

Sin reinstalar nadadesktop llega al binario por la salida por defecto de la función del rc, igual que session y auto. Solo necesitas ccp install si quieres que autocomplete.

El aislamiento son dos cosas

Y la segunda es la que no se ve. Sin ella el comando no serviría de nada:

Qué queda aisladoCon qué
La identidad de la app: sesión, tokens, MCP, Cowork--user-data-dir
El Code tab: credenciales de CLI, projects/, historial, agentesCLAUDE_CONFIG_DIR en el entorno del proceso
Por qué importaEl Code tab no lee el --user-data-dir: lee CLAUDE_CONFIG_DIR del entorno del proceso Desktop, y cae a ~/.claude cuando está vacía. Con solo lo primero, dos ventanas con cuentas distintas compartirían credenciales de CLI, historial y agentes. ccp desktop emite las dos, así que la ventana entera queda en el mismo perfil que tu terminal.

Qué cambia en el cc-home del perfil

Desktop rechaza symlinks de directorio bajo su config root, y ccp profile add siembra justo eso. La primera vez que abres una instancia, ccp convierte esas entradas en directorios reales cuyos archivos son symlinks al global.

  1. Sigues compartiendo commands/ y plugins/ en vivo con ~/.claude.
  2. agents/ y skills/ pasan a ser del perfil: cada perfil puede tener sus propios agentes.
  3. Un archivo tuyo dentro del perfil gana sobre el global y no se pisa al re-espejar.
¿por qué symlinks solo en los archivos?

Desktop valida lo que llama el co-writable boundary y rechaza un symlink en cualquier componente no-hoja del path que toca. Un commands/ que es symlink revienta en cuanto la app escribe en commands/algo.

Pero la regla exime la hoja. Por eso el espejo replica el árbol con directorios reales y deja el symlink solo en el archivo final: se conserva el compartido en vivo sin dejar un symlink en posición prohibida.

Si añades archivos nuevos al global, vuelve a espejarlos con ccp desktop prepare <perfil>.

Un lanzador por perfil: nombre e icono de color propios

Todas las instancias siguen siendo el mismo Claude.app, así que el Dock, Cmd-Tab y Spotlight enseñan iconos «Claude» idénticos. ccp desktop app construye un lanzador por perfil en ~/Applications —Claude (work-1).app— con nombre propio y el icono de Claude tintado de un color propio.

Construir los lanzadores.

ccp desktop app

Uno por perfil official, colores asignados solos. ccp desktop app work-1 --color purple elige uno (blue, green, purple, pink, teal, yellow, red, gray, orange o #rrggbb) y --label cambia el nombre. Desde entonces ccp desktop open work-1 —y un clic en el lanzador desde Spotlight o el Dock— abre la instancia de ese perfil con esa identidad; --plain lanza Claude.app directamente, como antes. ccp desktop app rm work-1 quita el lanzador; la instancia y su sesión se quedan.

La sesión se conservaEl lanzador no es una copia retocada de la app —eso pierde la cuenta, porque el Keychain deja de fiarse del proceso. Dentro hay un espejo del Claude.app real hecho de hard links, byte a byte el original y sin disco extra, y el lanzador es el propio ccp: pone --user-data-dir y CLAUDE_CONFIG_DIR y le cede el proceso a Claude.
Las actualizaciones siguen llegandoEl espejo fija la versión con la que se construyó, así que actualizar Claude.app nunca rompe un lanzador: en su siguiente arranque ccp ve la versión nueva y lo reconstruye. Claude se actualiza desde la instancia normal, como siempre, y todos los lanzadores lo siguen —igual tras ccp upgrade.

Gestionar las instancias

Ver cuáles existen y cuánto ocupan.

ccp desktop list

--json devuelve profile, data_dir, exists, bytes, app y color; siempre un array, con default de primero.

Borrar una instancia.

ccp desktop rm work-1 --yes
CuidadoEs un logout que se lleva la sesión, los tokens y la config MCP de esa instancia. Por eso exige --yes.

·Avanzado · Versiones

Actualizar ccp

De una versión anterior a la última. Tu config se migra sola; no pierdes perfiles ni reglas.

¿Qué versión tengo?

Imprime la versión del binario.

ccp version     # → 2.12.0

También vale ccp --version o ccp -v.

Subir a la última

Un comando. Reinstala el binario y re-sincroniza tus perfiles.

ccp upgrade

Descarga el binario de release para tu OS/arch, verifica su sha256, y luego regenera cada cc-home. Si no hay release pero sí toolchain de Go, compila desde fuente.

¿qué hace por dentro?

1. Lee ~/.config/ccp/install-source (la ruta del repo, registrada al instalar).

2. Re-ejecuta install.sh desde ahí: detecta OS/arch, baja el binario, verifica checksum, y borra las libs viejas de bash (~/.local/lib/ccp).

3. Corre ccp profile sync para regenerar la config de cada perfil.

Si el bloque de shell quedó viejo, te avisa: corre ccp install y recarga (source ~/.zshrc).

Variantes.

ccp upgrade --pull       # git pull en el repo antes de reinstalar
ccp upgrade --no-sync    # solo el binario, no toca los perfiles

Re-sincronizar sin reinstalar

Regenera CLAUDE.md + settings.json de cada perfil, re-fundiendo global ⊕ overlay. Útil tras cambiar tu config global o el overlay de un perfil.

ccp profile sync          # todos
ccp profile sync work     # solo uno

No toca default (no tiene overlay ni cc-home).

Vienes de la versión legacy (Bash / dsctl)

La migración es automática y perezosa: la primera vez que corras cualquier comando de ccp que toque la config, convierte tu estado viejo a ccp.yaml (schema v2). No tienes que hacer nada especial.

Qué pasa exactamente Antes de tocar nada, ccp respalda todo en ~/.config/ccp/.backup-pre-go-<fecha>. Crea un perfil deepseek con tu config DeepSeek vieja (la API key se mueve a api_key, chmod 600) y convierte tus reglas: las de include → deepseek, las de exclude → default. Es idempotente: corre cuantas veces quieras, migra una sola vez.

Después, quita el bloque viejo de tu shell — está en el Caso 07 · Vengo de dsctl.

·Avanzado · Respaldo

Exportar e importar tu configuración

Llévate todo a otra máquina, o respáldalo antes de un cambio grande. Todo cabe en un .tar.gz.

Exportar

Crear un respaldo (sin secretos).

ccp backup export ~/ccp-backup.tar.gz

Incluye manifest.yaml, tu ccp.yaml y los overlays de cada perfil. El archivo queda chmod 644.

Incluir secretos (API keys + logins oficiales).

ccp backup export ~/ccp-backup.tar.gz --with-secrets
CuidadoAñade tu api_key de DeepSeek y las credenciales OAuth de los perfiles oficiales (.claude.json). El archivo se escribe chmod 600. Guárdalo en un lugar seguro y nunca lo subas a git.
¿qué entra y qué no?

Siempre: manifest.yaml (con checksums sha256), ccp.yaml, y overlay/ de cada perfil.

Solo con --with-secrets: profiles/<n>/api_key y cc-home/.claude.json.

Nunca: los symlinks (plugins/ commands/ agents/ skills/). Se vuelven a crear solos al restaurar.

Importar / restaurar

Restaurar en otra máquina (o sobre esta).

ccp backup restore ~/ccp-backup.tar.gz

Por defecto: no pisa nada. Crea los perfiles que falten y fusiona las reglas (rutas nuevas se agregan, las tuyas se conservan).

Modos de colisión — qué pasa con lo que ya tienes:

ComandoPerfiles existentesReglas
restorese conservan; solo agrega los nuevosfusiona
restore --overwritereemplaza los que vengan en el backupfusiona
restore --forceborra todo y restaura limpioreemplaza todo
Red de seguridadAntes de tocar nada, ccp guarda un snapshot automático en ~/.config/ccp/.backup-pre-restore-<fecha>. Si algo sale mal, ahí está tu estado anterior. Y si el backup viene de un ccp más nuevo (schema superior), el restore aborta sin tocar nada: actualiza ccp primero.
·Avanzado · YAML

Configurar a mano (ccp.yaml)

Todo vive en un solo archivo. Puedes tocarlo con comandos o editarlo a mano: ambos caminos llevan al mismo YAML.

Con comandos

Ver los defaults actuales.

ccp config show

Cambiar un campo de los defaults. Claves: base_url, model_pro, model_flash, effort.

ccp config set model_pro deepseek-reasoner

Solo afecta a los perfiles deepseek que crees después. Los existentes guardan sus 4 campos explícitos.

Volver los defaults a fábrica · elegir editor.

ccp config reset
ccp config editor nano     # o vim, code, etc.

Abrirlo sin romperlo — ccp config edit

Editar el archivo y que ccp te lo revise al cerrar el editor.

ccp config edit                        # abre ccp.yaml, y al cerrar lo relee y valida
ccp config edit --profile personal-1   # abre el overlay de ese perfil
ccp config edit --terminal             # fuerza el editor de terminal
ccp config gui-editor "code -w"        # fija el editor gráfico

El editor es el primer escalón que exista: --editor <cmd> → defaults.gui_editor → $VISUAL → VS Code y familia en el PATH (code → cursor → code-insiders, invocados con -w) → lanzador del SO (open -W -t, notepad, xdg-open) → defaults.editor / $EDITOR / nano. El comando te dice qué escalón ganó.

El -w ES la decisión, no un detalle. code archivo retorna al instante, y sin esperar a que el editor cierre no se puede hacer lo único que da valor real al comando: releer el yaml y validarlo. Un ccp.yaml roto por una edición gráfica no se manifiesta al guardar — se manifiesta en el siguiente ccp session, en mitad de un salto, con un error de parseo a las 3am. Por eso, cuando el editor bloquea, ccp recarga el archivo y comprueba la semántica de auto_handoff (cada política por Effective(), cada perfil del fallback existiendo de verdad) y nombra la clave y el valor ofensivos si falla.

Un editor que no bloquea recibe un aviso, no una mentiraCon xdg-open —o code sin -w— el comando retorna antes de que hayas escrito nada, así que no hay nada que validar. ccp lo dice por delante en vez de fingir. También en --profile, donde además no regenera el cc-home (hacerlo ahí lo reconstruiría desde el contenido previo a la edición) y te manda a ccp profile sync <perfil> para cuando termines.

El archivo, anotado

Vive en ~/.config/ccp/ccp.yaml (o $CCP_HOME/ccp.yaml).

oficial vs deepseek

Un perfil oficial guarda solo type: official; su login vive aparte, en cc-home/.claude.json.

Un perfil deepseek guarda los 4 campos (base_url, model_pro, model_flash, effort) explícitos, sin herencia. defaults solo los siembra al crearlo.

Reglas de oro 1. default es implícito: nunca lo pongas en profiles. Es tu login normal y gana cuando ninguna regla aplica. Para una excepción, usa profile: default en una regla.
2. Las rutas en rules son absolutas y normalizadas (sin ~). Mejor deja que ccp las normalice con ccp path set ~/x perfil.
3. La API key no va aquí: vive en ~/.config/ccp/profiles/<n>/api_key (chmod 600). Edítala con ccp key <n>.
¿es seguro editarlo a mano?

Sí. ccp escribe de forma atómica (tmp + rename) bajo un flock, conserva tus comentarios y cualquier clave desconocida en round-trip.

Guard de versión: si version es mayor que la que tu binario conoce, ccp se niega a leer o escribir y no toca el archivo. Actualiza ccp.

Tras editar a mano: refresca el hook con cd . y verifica con ccp status · ccp path list.

·Ayuda

Solución de problemas

Toca una pregunta para ver la respuesta.

+ccp: command not found

~/.local/bin no está en tu PATH. Vuelve al Paso 2 de Instalación.

+ccp use … no cambia nada / "Función 'ccp' no cargada"

Falta cargar la función de shell. Corre ccp install y luego source ~/.zshrc (o ~/.bashrc).

+Cambié de carpeta y el perfil no cambió

El hook recuerda la última carpeta. Tras editar reglas, refresca con cd .

+Al abrir Claude dice "Not logged in"

Ese perfil oficial todavía no tiene sesión. Inícialo una vez con ccp profile login <nombre>.

+Quiero ver el perfil de una carpeta sin entrar en ella

Usa ccp resolve ~/ruta/que/sea

+¿Cómo cambio el idioma de la salida?

Corre ccp lang en|es, usa CCP_LANG=es, o pulsa L en el dashboard interactivo (TUI).

+¿ccp cambia algo dentro de Claude Code?

No. Solo apunta Claude Code a un perfil por carpeta (su propio config dir / proveedor). Tus cuentas y ajustes quedan intactos.

+¿Dónde se guardan mis API keys?

En ~/.config/ccp/profiles/<nombre>/api_key, chmod 600. Nunca en ccp.yaml, en el rc del shell, ni en git.

+¿Cómo actualizo ccp?

Corre ccp upgrade — re-ejecuta el instalador y profile sync.

+¿Cómo desinstalo?

Corre ccp uninstall para quitar el bloque del shell; opcionalmente rm -rf ~/.config/ccp para borrar config y perfiles.
