# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`ccp` (profiles for Claude Code) is a CLI (Go, v2.0) that routes Claude Code to a named **profile** per terminal and per directory — never global. A profile is one of: an **official** Anthropic account (its own `CLAUDE_CONFIG_DIR`), a **DeepSeek/compatible provider** (its own `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` + models), or the reserved **`default`** (the user's normal `~/.claude` login). So repo A → account *work*, repo B → account *personal*, repo C → *deepseek*. User-facing strings are bilingual (English default, Spanish via `ccp lang es` / `CCP_LANG=es`).

`ccp` was **rewritten from Bash to Go** in v2.0 (plan: `docs/superpowers/plans/migracion-go-v2.md`). The Bash implementation is **archived in `legacy/`** and is now the **contract oracle**: the Go binary's observable surface is held byte-identical to it by a golden-diff gate. The chained migrator still auto-upgrades old state: the first Go run migrates `~/.config/dsctl` → `ccp` (TSV) → `ccp.yaml`, backing up first (`~/.config/ccp/.backup-pre-go-*`). The old rc block is unchanged (it only calls `command ccp`), so no rc reinstall is needed.

## Commands

```bash
go build ./...                 # compile (binary: ./cmd/ccp)
go test ./...                  # unit tests (core/cli) + golden gates
gofmt -l internal cmd          # must print nothing (CI gate)
go vet ./...                   # CI gate
golangci-lint run              # CI gate — CI pins v2.12.2 (golangci-lint-action@v8)
# reproduce CI exactly without installing anything:
#   go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.12.2 run --timeout 5m
# `.golangci.yml` is in the v2 schema (`version: "2"`); a v1 binary cannot read it.

bash legacy/tests/run.sh       # bash ORACLE suite (still a CI gate)
bash testdata/golden/capture.sh --check   # oracle reproduces committed golden
bash testdata/golden/capture.sh           # regenerate golden from the oracle
```

The **parity gate** lives in `internal/golden/parity_test.go`: it builds the Go binary, runs it over the `testdata/golden/basic` fixture, and asserts its stdout + exit code match the committed `expected/` (which were captured from the bash oracle by `capture.sh`). Green ⇒ Go == bash on the frozen contract (`_env`, `_hook`, `resolve`, `path test`, `status --json`, `completion bash|zsh`, `completion-shellinit`). When you change any of those, update the bash oracle in `legacy/`, regenerate the golden with `capture.sh`, and keep the parity test green.

Always run the binary in tests with a temp `CCP_HOME` (an existing dir) so auto-migration does not fire against real `~/.config/dsctl`.

Auto-handoff surface (added on top of the frozen contract). `session` and `auto` are **not** shell-only: they reach the binary through the `*) command ccp "$@"` fallthrough, so no rc reinstall. `handoff prune`/`sessions` **do** need one — `handoff` is intercepted by the shell function, and the read-only passthrough list in `ShellInit` had to gain `prune|sessions` (an rc installed before that forwards them to `_handoff` as if they were a target profile; the binary detects it and says to run `ccp install`).

```bash
ccp session [-p|--headless] [--policy <n>] [--max-hops N] [--yolo] \
            [--session <uuid>] [--dry-run] [--no-return] [--claude-bin <path>] [-- <claude args>]
ccp auto init [--force] | install [<profile>…] | uninstall [<profile>…] | status [--json] | test [--profile <n>]
ccp handoff prune [--keep N] | sessions [--json]
ccp _statusline [-- <wrapped cmd>]   # internal sensor: persists rate_limits, always exits 0
ccp _limit-hook                      # internal StopFailure hook: writes a sentinel, always exits 0
```

`ccp session` exit codes: `0` ok · `1` usage/config · `2` handoff I/O (`core.ErrHandoffIO`) · `75` all profiles exhausted (`supervisor.ParkedExitCode`, EX_TEMPFAIL) · otherwise the child's own code.

Desktop surface (also additive, also reachable through the `*)` fallthrough — no rc reinstall; `ccp install` only refreshes completion).

```bash
ccp desktop open [<profile>] [--app <path>] [--dry-run] [--no-mirror] [--plain] [--force] [-- <claude args>]
ccp desktop app [<profile>…] [--color <c>] [--label <name>] [--app <path>] [--force] [--dry-run]
ccp desktop app rm <profile> | app list [--json]
ccp desktop list [--json] | path <profile> | prepare <profile> | rm <profile> --yes
ccp desktop doctor [<profile>] [--json]   # audita lanzadores, instancias e identidad; no repara
ccp desktop sessions [<profile>] [--archived] [--json]   # sesiones de la pestaña Code de cada ventana
ccp desktop copy <uuid|title> <profile> [--from <profile>] [--no-open] [--dry-run]
```

`ccp desktop copy` lleva una conversación de la pestaña Code a la ventana de otro perfil ([ADR 0010](docs/adr/0010-desktop-session-copy-via-import-link.md)): copia el transcript y le pide a Desktop que lo importe con `claude://resume?session=<uuid>`. Salida `0` solo si la sesión queda en la barra lateral del destino (o, con `--no-open`, copiada); `1` en cualquier otro caso, incluido «copiada pero sin importar», que siempre dice qué hacer. En los tests, `CCP_DESKTOP_DEFAULT_DATA_DIR` sustituye el data dir de la ventana de `default` (`~/Library/Application Support/Claude`).

`ccp desktop doctor` es el diagnóstico que faltaba el 2026-09-15 (el incidente entero y por qué la identidad no se puede garantizar están en [ADR 0009](docs/adr/0009-desktop-identity-is-not-durable.md), que enmienda al [0008](docs/adr/0008-desktop-launcher-two-layer-bundle.md)). Motor puro en `core/desktop_audit.go` con las sondas **inyectadas** (`ps` y `lsappinfo` entran como funciones), así que el estado corrupto se monta en un test sin abrir una ventana. Regla que no se negocia: **una sonda que no se puede ejecutar produce `unknown`, jamás `ok`** — un doctor que dice «todo bien» porque no pudo mirar convierte una duda en falsa certeza. No repara nada a propósito: borrar lanzadores o reconstruir bundles desde un diagnóstico lo convertiría en una segunda fuente de pérdida. Códigos: `instance_foreign_exec` · `instance_no_config_dir` · `instance_wrong_config_dir` · `instance_updater_on` · `launcher_mirror_stale` · `launcher_mirror_orphan` · `launcher_profile_gone` · `launcher_identity_collapsed` · `instance_multi_account` · `probe_unavailable`. Ese penúltimo existe para decir la frase que nadie dijo a tiempo aquel día: las sesiones se indexan por `<cuenta>/<org>`, así que las que no se ven **no se han borrado**, vuelven al entrar con esa cuenta.

`desktop open` cambió de comportamiento en tres puntos, los tres por lo ocurrido: si el perfil no tiene lanzador **lo construye** en vez de caer al camino directo (sin él la ventana corre desde `/Applications/Claude.app` y macOS no la distingue del Claude del usuario); el `-n` deja de ser incondicional, de modo que `default` **activa** su ventana en lugar de abrir un segundo Chromium sobre el data dir real, salvo que una instancia ajena tenga secuestrado el bundle id, que es cuando sí hace falta forzarla; y `launchDesktop` fija el entorno del hijo **también en darwin** (`plan.CleanEnv`) — `open` hereda el entorno de quien lo invoca y `--env` solo sobrescribe lo que nombra, así que lanzar desde una terminal con un perfil deepseek activo metía su `ANTHROPIC_BASE_URL` viva en una instancia *official*. `--force` se salta el preflight cuando el usuario sabe lo que hace.

`core/desktop_preflight.go` es el sensor, y también puro: `ParseDesktopProcs` lee `ps -Ewww -axo pid=,command=` (la combinación importa: `-E` da el entorno pero solo se ve con `-ww`) y `DesktopPreflight` clasifica. Sustituye a la pregunta vieja «¿hay algo con este `--user-data-dir`?», que era **ciega al ejecutable**: el proceso patológico `/Applications/Claude.app/… --user-data-dir=<perfil>` contaba como instancia sana, así que el detector bendecía justo el estado que había que corregir y de paso bloqueaba la reconstrucción que lo habría arreglado.

## Architecture

The binary/shell-function split is the central design constraint and is **unchanged** by the rewrite — the Go binary just emits the same shell tail the bash did:

- **`cmd/ccp` + `internal/cli`** — the CLI binary. Dispatch is by hand (no cobra) so the bash/zsh completion is emitted **verbatim**. Runs in a child process, so it **cannot** mutate the parent shell's environment.
- **Shell function `ccp`** — emitted by `core.WriteShellInit` (the bash heredoc ported to a Go string constant, byte-identical) and appended to the rc by `ccp install`. Because it runs *in* the shell, only it can `export`/`unset`. It intercepts `use <perfil>` / `default` / `off` / `on` / `run`, applying the env delta via `eval "$(command ccp _env <perfil>)"`; everything else falls through to `command ccp "$@"`.
- **`_ccp_autocheck` hook** — runs on every prompt (zsh `precmd_functions` / bash `PROMPT_COMMAND`), caches by `$PWD`, applies the resolved profile via `eval "$(command ccp _hook "$PWD")"`. This is why `cd` alone flips the profile.

So: env mutation lives in the rc-installed function; all logic lives in the binary; the binary EMITS env (`ccp _env`/`_hook`); the shell EVALs it — the only place env changes.

### `internal/core` (the engine — no presentation I/O)

Returns data/strings; the front-ends format. The exceptions are `env.go` and `shellinit.go`, which produce exact strings because they ARE the contract.

- **`rules.go`** — pure resolver. `Resolve(query, rules)` returns the **profile name**: among rules whose path is P or an ancestor, the **deepest** wins; no match → `default`. `rules_cmd.go` does the CRUD (`RuleSet/RuleDel/RulesClear/RulesList`) over `ccp.yaml`. `NormalizePath` resolves `.`/`..`/`~` textually (not `realpath`).
- **`profile.go`** — profile CRUD on an explicit `home` arg (`ProfileAddOfficial/AddDeepseek/Rm/List/Show/SetKey`). Seeds each non-`default` profile's `cc-home` (symlinks `plugins/ commands/ agents/ skills/ output-styles/ hooks/` and the file `keybindings.json` from `~/.claude`; the last three since Fase 0, B4). `seedCCHome` never touches an entry that exists, and `ProfileSync` calls it too — that is how a profile created before the list grew gets the new entries, since `ccp upgrade` ends in a sync. Adding an item means touching `desktopMirrorItems` too (directories only) and `_seed_cc_links` in the bash oracle. `ProfileAddOfficial`/`ProfileAddProvider` also generate the config right after seeding (`profileGenerateConfig` → `CfgRegenerate`: overlay + `cc-home/CLAUDE.md` + `settings.json`), like the oracle's `_seed_cc_home` (B8). If that fails the profile stays created and the error is a `*ProfileConfigError`, so the CLI and the TUI translate the frame (retry with `ccp profile sync <n>`) and the TUI still saves the API key. `ProfileRename` returns `RenameResult{Relogin}`: official + `HasLogin`, decided **before** moving. The Keychain name follows the cc-home path (M4) and ccp never touches the Keychain, so all three front-ends print the hint (B7); the CLI and the TUI also print it behind a regeneration error, because by then the directory has already moved. `HasLogin` keeps saying "logged in" after a rename, because `oauthAccount` travels with `.claude.json`: the hint is the only signal.
- **`env.go`** — `EnvDelta(home, profile, cfg)` emits the eval-able delta: always `unset` all managed vars first, then `export` the target's. Every value is quoted by `shellQuote`, a hand-rolled replica of bash `printf %q` (NOT `strconv.Quote`) — this is contract risk #1; it has a dedicated test plus an eval-effect test in zsh+bash.
- **`store.go`** — reads/writes the canonical `ccp.yaml` (atomic tmp+rename under a `flock`; preserves comments + unknown keys; aborts if the file's schema version is newer than this binary knows).
- **`migrate.go`** — the universal chained migrator dsctl→ccp(TSV)→`ccp.yaml`, idempotent, backs up before touching anything.
- **`doctor.go`** — `HasLogin`/`DefaultHasLogin` decide «logged in» by the **account recorded** in `.claude.json` (`oauthAccount` non-empty or `primaryApiKey`), never by the file existing: Claude Code creates it on first start, before `/login` (B3). `doctor`, `profile show`, the TUI and `serve` all go through it.
- **`backup.go`** — `BackupRestore` regenerates (`CfgRegenerate`) every created/overwritten profile after `Save`, and reports them in `RestoreReport.Regenerated` (B2); before, `cc-home/settings.json` and `CLAUDE.md` stayed stale until a `profile sync`.
- **`cfg.go`/`cfg_cmd.go`** — profile-config overlay: `cc-home/CLAUDE.md` = `@import`s of global + overlay; `cc-home/settings.json` = a **pure-Go** deep-merge of global ⊕ overlay ⊕ **auto layer** when `AutoHooksEnabled` (no `jq`). `secrets.go`, `backup.go`, `instruct.go`, `doctor.go`, `status.go`, `shellinit.go` round it out.
  - **The `/config` drift (B6, `cfg_drift.go`).** `cc-home/settings.json` is generated, but it is also that profile's *user* settings file: `/config`, `/model` and `/permissions` write there. `CfgRegenerate` adopts, in **every** path that regenerates (sync, `profile config`, `instruct add`, the GUI's `overlay.envSet`, both restores, the rename), what was changed by hand into the overlay before overwriting it — if only `profile sync` adopted, any other path would drop it as before. The baseline is **two** copies in `profiles/<n>/state/`: `last-settings.json` (what was last generated) and `last-overlay.json` (the overlay it was generated from), `0600`, tmp+rename, never captured by snapshots or backups. The overlay copy is what makes "did the overlay change since then?" exact; comparing the overlay against the generated file was an approximation that broke when the auto layer wrapped an overlay key (`statusLine`), when the overlay held something the strip removes (`"hooks": {}`) or when the overlay *deleted* a key. If either can't be written, both are deleted and the regeneration fails, because a stale baseline would take the global's changes for drift and freeze them into the overlay.
  - Rules, in order: an invalid `cc-home/settings.json` → copy to `state/settings.invalid-<hash>.json` + warn, checked **before** the baseline (if the copy can't be saved, the regeneration fails without overwriting); no baseline, or an unreadable one → nothing is adopted, but if what is there differs from what will be generated a **rescue copy** is kept first (`Unattributed`); the auto layer is stripped from `last`, `cur` and `exp` (`stripAutoLayer`, which shares `isCCPStatusLine` and `isCCPStopFailureEntry` with the regeneration, so "ours" has a single definition); only what the regeneration would lose is adopted, measured against global ⊕ overlay **without** the auto layer (`cfgBuildUserSettings`); a key whose overlay value (or presence) differs from `last-overlay.json` is a conflict and the overlay wins; **`env.*` is never adopted** (`Skipped`: it usually holds tokens, and the overlay travels in clear in "secret-free" backups and in snapshots, while `cc-home/settings.json` does not); removals are only warned, and only when the key would come back. If the overlay can't be written (a symlink into a read-only dotfiles store), the would-be adoptions become `Unsaved` — never `Adopted` — and the regeneration still runs: adopting is an extra that must not turn a regeneration that used to work into an error. Anything the user wrote that does not reach the overlay (conflicts, skipped, unsaved) leaves a rescue copy `state/settings.rescued-<hash>.json` (content-addressed so two copies never overwrite each other, last 20 kept). The diff follows `MergeJSON` (recurse only into objects; arrays and scalars are whole) and compares numbers by value (`big.Rat`), because Claude Code rewrites the file with `JSON.stringify` and `30.0` → `30` is not a user change. `cc-home/settings.json` itself is written with tmp+rename: Claude Code and the Code tab read it live.
  - **Nobody drops a report.** `CfgRegenerate` and `ProfileSync` (the wrappers that don't count) save a non-empty drift to `state/drift-pending.json`; `ProfileSyncReport` returns each profile's pending drift before its fresh one and clears it; `ccp profile config` and `ccp instruct add … profile hook` print it right after their regeneration; `profiles.sync` re-saves what it collected when it fails halfway (an error reply carries no result). `NotRegenerated` marks a drift whose regeneration failed afterwards, so the CLI never says "regenerated" over an error.
  - `CfgRegenerateReport`/`ProfileSyncReport` return the `SettingsDrift` (`Adopted`/`Removed`/`Conflicts`/`Invalid`); `CfgRegenerate`/`ProfileSync` are wrappers that drop it, for the callers that don't count. The overlay is rewritten via tmp+rename keeping its mode, following a symlink (a dotfiles repo stays linked), sorted by key like `OverlayEnvSet`.
- **`envpairs.go`** — `EnvPairs`/`EnvForChild`: the same delta `env.go` emits, as data instead of shell text. `EnvForChild(os.Environ(), …)` is how the supervisor gives a child process a profile's environment without a shell to `eval` in.

Auto-handoff engine (all of it additive; `ccp.yaml` stays at schema `version: 2` and `handoffs.yaml` at `2`, so an older binary preserves the new keys instead of refusing the file):

- **`auto.go`** — the `auto_handoff` block: `AutoPolicy.Effective` (defaults + validation, duration strings parsed once) and `ResolveAutoChain(home, cfg, policy, cwd)` → `{Policy, Primary, Fallback, Denied}`. `Primary` is `Resolve(cwd, cfg.Rules)` and is dropped from `Fallback` silently (it's implicit). `AutoInit` seeds the block. The `allow_from` gate has three states and the third is the point: **map absent/empty ⇒ no gate; declared with an entry for the primary ⇒ only that entry passes; declared without an entry ⇒ total deny.**
- **`ratelimit.go`** — pure parsers, no I/O: `ClassifyLimitText` (window from CC's prose), `ParseTranscriptLine`, `ParseStreamJSONLine`, `ParseStatusLineInput`, `ReadCachedUsage(ccHome)` (`.claude.json` → `cachedUsageUtilization`), and `RateLimits.Exhausted(threshold)`. Everything normalizes to a `LimitEvent{Window, ResetsAt, Source, Detail}`.
- **`autostate.go`** — sensor state under `<home>/state/auto/`: `rate-limits/<profile>.json` (last statusLine sample) and `sentinels/` (what the StopFailure hook leaves). Profile/session names are sanitized to `[a-zA-Z0-9._-]` before they become filenames — the values come from a hook payload, i.e. from outside.
- **`autohooks.go`** — the managed settings.json layer: `AutoHooksFragment` (`hooks.StopFailure` → `ccp _limit-hook`, `statusLine` → `ccp _statusline -- <the user's own>`), `ExtractStatusLineCommand` (returns `""` for our own command, which is what stops the wrapper from wrapping itself every regeneration), and `keepForeignStopFailure` (needed because `MergeJSON` *replaces* arrays). The binary path is package state (`SetAutoHooksBin`, injected once from `internal/cli` via `os.Executable`) so `auto install` and `profile sync` can't write two different values.
- **`transcript.go`** — the JSONL operations. Two rules that are easy to undo by accident. `RewriteSession` reads with a `bufio.Reader`, **never a `Scanner`**: a Scanner forces a per-line ceiling and any ceiling here is a permanent failure — one line with a pasted image or a large `tool_result` used to blow the 8 MB cap, and since `CopyTranscript` (the outbound leg) never had one, the session could be lent and then **never** returned, leaving `discard` as the only exit. And both writers go through `writeTranscriptAtomic` (tmp+rename): the transcript is the one piece of state ccp cannot reconstruct, and a truncating write interrupted halfway leaves a half-written `.jsonl` *under the real uuid*, which is worse than nothing because `claude --resume` finds it. The temp name is random (`HandoffAdoptHome`'s rewrite runs outside the flock, so two processes can target the same path) and its suffix must **not** be `.jsonl`, or `ListSessions` would offer it in the session picker. A session's title has **one** reader, `TranscriptTitle` (`desktop_sessions.go`), shared by `ccp handoff` (`ListSessions`, the marker's `Title`) and `ccp desktop sessions`: the last non-blank `customTitle`, else the last `aiTitle` — Claude Code's order. Desktop's Code tab titles every session with `custom-title` and never writes `ai-title` (the CLI's `/rename` writes `custom-title` too), so the old `aiTitle`-only reader showed every Desktop session as untitled. That is also why `RewriteSession` marks **both** fields with `[de <perfil>]`: marking only `aiTitle` leaves the mark invisible whenever a `customTitle` exists. Blank titles are left unmarked, because the reader ignores them and a prefix would turn one into the title.
- **`handoff_chain.go`** — `HandoffChain` lifts the no-chain invariant *for the supervisor only* by **mutating the live marker in place** (`To = to`, `Hops += to`; `From`/`Since` untouched) instead of stacking a level, so `handoff end` still comes home in one step. Fan-out stays forbidden. `HandoffEndSession` is `HandoffEnd` minus the shell emit (returns the closed marker and the new uuid); `HandoffPrune(home, keep)` trims `archived`.

Desktop instances (additive too; no schema change, no new `ccp.yaml` keys).

- **`desktop.go` / `desktop_launch.go`** — one isolated Claude Desktop instance per profile. The isolation is **two** things and the second one is the whole point: `--user-data-dir` moves the app's identity (session, tokens, MCP, Cowork), but the **Code tab inside Desktop does not read it** — it reads `process.env.CLAUDE_CONFIG_DIR` (`function lT(){return process.env.CLAUDE_CONFIG_DIR}` in `app.asar`, falling back to `~/.claude`), so without injecting the profile's env at launch two windows on different accounts share credentials, `projects/` and agents. `PlanDesktop` is pure (GOOS/LookPath/Stat injected) and emits both; it **never emits an empty-valued var**, because Desktop resolves the root with `??`, which only falls back on null/undefined — an empty `CLAUDE_CONFIG_DIR` would set the config root to `""`. Only `official` profiles and `default` are eligible (Desktop ignores `ANTHROPIC_BASE_URL`, so a provider profile would put the Code tab on DeepSeek while the chat half stays Anthropic). `default` is never relocated: its instance is the user's normal one.
  - **`MirrorForDesktop` exists because of a hard conflict with `seedCCHome`.** Desktop refuses symlinks at any **non-leaf** component under the config root (`symlink at a non-leaf component below the co-writable boundary`), and `seedCCHome` seeds exactly that (`cc-home/commands -> ~/.claude/commands`). `seedCCHome` is **not** changed — the bash oracle asserts `[[ -L "$cch/plugins" ]]`, so the symlinked shape *is* the contract of `profile add`. Instead the conversion is opt-in and per-profile: real directories mirroring the global tree, symlinks only at the **file** leaves (which the rule exempts, since it walks `c[0..len-2]`). Live sharing with `~/.claude` survives; `agents/` becomes a real per-profile directory. Two rules carry it: an entry that already exists is never touched (idempotence + profile-level override), and only dangling links pointing **inside** the global source are pruned. `DesktopMirrorPending` is the same classification without touching disk, so `--dry-run` is actually dry.
- **`desktop_app.go`** — the per-profile launcher `~/Applications/Claude (<profile>).app` (`ccp desktop app`): what gives each instance its own name and icon colour in the Dock/Cmd-Tab/Spotlight. It is a **two-layer bundle**, and every layer exists because of a fact established by experiment on macOS 26 — undo any of them and something concrete breaks:
  - The **outer** layer is what LaunchServices sees: a patched copy of Claude's `Info.plist` (own `CFBundleIdentifier`, `CFBundleName`/`DisplayName` = the label, `CFBundleIconFile` = the tinted `.icns`, no `CFBundleIconName` — on macOS 26 the Assets.car icon would win — and **no `CFBundleURLTypes`**, so `claude://` and the login callback keep going to the real app). Its `CFBundleExecutable` is a **hard link to the ccp binary** (a copy if the volume refuses links): LaunchServices launches *nothing* through a symlinked executable (`open` returns 0), and a script makes it pick the x86_64 slice (Rosetta), where Chromium dies. `cmd/ccp/main.go` checks that invocation first (`IsDesktopLauncher`: an executable named `Claude` under `Contents/MacOS/` next to a `ccp-desktop.json` manifest) and runs `RunDesktopLauncher`, which builds the profile env (`EnvForChild`) + `--user-data-dir` and `syscall.Exec`s `Contents/MacOS/Claude-run`.
  - `Claude-run` is a symlink into the **inner** layer, `Contents/ccp/Claude`: a pristine mirror of `/Applications/Claude.app` (real directories, files as hard links, symlinks recreated). Pristine is the whole point: the Keychain ACL on «Claude Safe Storage» — the key Chromium encrypts the session with — validates the process by its **real** path (`proc_pidpath`), and it validates only if the enclosing bundle is byte-identical to a signed one *and* the running executable is that bundle's `CFBundleExecutable` (a pristine plist with the stub merely renamed still fails with `errSecAuthFailed`). LaunchServices, on the other hand, identifies the process by the innermost bundle of the **unresolved** exec path, and `Contents/MacOS/Claude-run` is in the outer layer — so the Dock shows the launcher. **That identity is real but not durable, and the difference cost a user an entire afternoon on 2026-09-15.** macOS keeps two paths for the same process: the one passed to `execve` (what `_CFProcessPath`, `[NSBundle mainBundle]` and the LaunchServices check-in use — measured: `ps` reports the symlink) and the resolved vnode (what `proc_pidpath`, Security.framework and TCC use — measured: `lsof txt` reports the target). The two-layer trick lives in that gap, so it holds only while the process is the one the kernel exec'd *through* `Claude-run`. Electron's `process.execPath` comes from `uv_exepath`, which calls `realpath()`, so **any** re-exec or `app.relaunch()` reincarnates the process as `com.anthropic.claudefordesktop` located in `Contents/ccp/Claude`, and it never comes back. From that moment `open -a /Applications/Claude.app` only ACTIVATES the profile window — the user cannot open their own Claude — and a `claude://` login callback can land in the wrong one. The three levers to recover identity are measured and closed: a hard link for `Claude-run` (moves `proc_pidpath` into the outer layer and kills the Keychain ACL, and the reported name is whichever of the inode's links the vnode cache holds, so it isn't even deterministic), `CFProcessPath` (ignored under hardened runtime) and `LSMultipleInstancesProhibited` (about user sessions, not instances). ccp therefore does not bet on identity: it detects the collapse (`ccp desktop doctor`) and keeps `default` reachable (`PlanDesktop` forces `-n` when a foreign instance holds the id). Chromium's helpers run in a sandbox whose `BUNDLE_PATH` is the main bundle (outer); the mirror is *inside* it, so the `subpath` rule covers it (with symlinks to `/Applications` the GPU and network helpers died with «Unable to find helper app»). Electron checks `app.asar` against `ElectronAsarIntegrity` of the main bundle by path relative to its `Contents/`, hence the duplicated entry under `ccp/Claude/Contents/Resources/app.asar`.
  - **Updates**: the hard links pin the inodes, so a Claude.app update leaves a launcher running the previous version rather than breaking it; `DesktopAppStale` (source `CFBundleVersion`, **mirror/source inode via `os.SameFile` — ShipIt replaces the bundle wholesale, so a reinstall of the *same* version orphans the links silently**, and only when both live on the same device, or `hardlinkTree` fell back to copying by construction; ccp binary size+mtime stamp; mirror/icon presence) makes the next launch — Dock or `ccp desktop open` — rebuild it, never while its instance runs (`desktopInstanceRunning`, via `ps`). **The instance CAN self-update, and did.** That claim used to say the opposite and it was false: SQRLUpdater compares against `NSRunningApplication.currentApplication.bundleIdentifier`, which after the collapse above *is* the real id, and its `targetBundleURL` resolves to whatever LaunchServices has under that id. On 2026-09-15 a profile instance moved `/Applications/Claude.app` from 1.52386.3 to 2.110.0 (`ShipIt_stderr.log`: «Beginning installation» → «Moved bundle contents … to file:///Applications/Claude.app/»), i.e. it updated the user's main app from a window he had opened for another account, and left its own mirror on the old version with its hard links orphaned. Hence the barrier in `desktop_env.go`: every profile instance is launched with `DISABLE_UPDATE_CHECK=1` — an undocumented flag, but present twice in `Squirrel.framework/Versions/A/Squirrel` next to `SQRLUpdater.m`, read once with `getenv()` at init — on **both** paths (`PlanDesktop` and `PlanDesktopLauncher`). `default` is deliberately exempt: that instance IS the user's Claude and muting its updates would be hijacking it. And because ShipIt replaces the bundle wholesale instead of patching it, `DesktopAppStale` also compares inodes (`os.SameFile`): a reinstall of the *same* version would otherwise leave the mirror orphaned forever, silently holding a full private copy of Claude on disk. The manifest lives in the bundle, not in `ccp.yaml`: derived state, regenerated whole, invisible to older binaries. Rebuilds go to a temp sibling and are swapped in, and a `.app` without a manifest is never touched.
  - `plist.go` is a minimal order-preserving XML plist reader/writer so the patching is testable on Linux (binary plists go through `plutil` on darwin); `icns.go` tints by rotating the hue of the PNG chunks (`ic07`+) and drops the rest. Palette in `DesktopPalette`; `orange` is the identity.
- **`desktop_sessions.go`** — moving a Code-tab conversation between windows (`desktop sessions|copy`, [ADR 0010](docs/adr/0010-desktop-session-copy-via-import-link.md)). A Code session is **two** things and ccp writes only one: the transcript (`<cc-home>/projects/<slug>/<uuid>.jsonl` plus the sibling `<uuid>/` folder with subagents and workflows), which ccp copies; and the entry in Desktop's index, `<data-dir>/claude-code-sessions/<account>/<org>/local_<id>.json` (title, cwd, `cliSessionId`), which ccp **reads** for titles and **never writes** — it is an internal format and the app holds it in memory. The destination's entry is created by Desktop itself through `claude://resume?session=<uuid>` (`importCliSession`, measured in app.asar 2.2553.1, present in 2.110.1). Three facts from that side shape the file, and undoing any of them breaks something: the import finds `<uuid>.jsonl` in any `<config-dir>/projects/*/` and reads the cwd from the transcript (so the copy keeps slug and uuid); it reads the title **only from the last 256 KiB** (`desktopTitleLine` appends a `custom-title` line when the title is not there — the first session moved by hand was imported untitled); and it **refuses a transcript with more than one hard link** (the copy is always a file of its own, `0600`, by tmp+rename via `writeFileAtomic`).
  - **The copy never overwrites a conversation.** `desktopCopyOutcome` compares bytes, in this order: missing → `new`; equal → `same`; destination is a prefix of what would be written → `updated`; destination already starts with the whole source → `ahead`, untouched (Desktop appends `custom-title`/`mode`/`atis-latch`/`last-prompt` lines just by opening a session, and then the user keeps writing there); destination minus its trailing **non-message** lines (no `uuid` key; an unreadable line counts as a message) is a prefix of the source → `updated` (the return trip of a loan); anything else → `ErrDesktopCopyDiverged`, nothing written. The CLI also refuses `updated` when the destination window is open **and** already indexes the session: it could have the old version loaded and would fork the conversation in the same file. The sibling folder follows the same rule per file (missing → copy, grown → update, different → kept and counted; symlinks are neither followed nor recreated).
  - **The link goes to one window, and only when that is safe.** `open -a <app>` — the profile's launcher, or the main Claude.app for `default` — never a bare `open`, which would hand it to whoever claims `claude://` (always the main app: launchers don't declare it). Measured: `open -a <launcher> 'claude://code/<probe>'` reaches that profile's running window without a second instance. `DesktopImportRoute` is pure with the probes injected (`ps`, `lsappinfo` via `ParseLSAppInfo`) and refuses on: no launcher (the window would run as the main Claude), a collapsed launcher identity, the main id held by another bundle path or by the main exe with a profile data dir, an instance without its `CLAUDE_CONFIG_DIR` (preflight fatal), or **any probe unavailable** — 0009's rule. Only the launcher path and its nested mirror (`Contents/ccp/Claude`) count for the collapse check: Chromium helpers hang from the launcher too, with their own `…helper` id, and counting them would call every live window collapsed. A window that already indexes the session is not asked again (two index entries on one transcript are two writers).
  - The import is **confirmed by reading the destination index** (`DesktopIndexed`, 20 s with the window open, 90 s when the link has to launch it), never inferred from `open`'s exit code. The system touchpoints in `internal/cli/desktop_sessions.go` (`desktopSendURL`, `desktopWaitIndexed`, `desktopImportProbe`, `desktopImportSupported`, `desktopProfileRunning`) are package vars so the import path is testable on Linux without opening anything. `ccp handoff` still copies only the `.jsonl` (no sibling folder) — unifying both copies needs `RewriteSession`'s new-uuid return trip to rename that folder too.
- **What a profile window actually reads — measured, not assumed** ([ADR 0016](docs/adr/0016-what-desktop-reads-from-a-profile.md), Claude.app 2.2553.1). Any projection work (subproject B) builds on these, and each one has a measurement behind it:
  - The Code tab runs **its own** Claude Code, downloaded per window into `<data-dir>/claude-code/<ver>/`, a different version from the user's CLI and from other windows. It launches it with `--setting-sources=user,project,local`, an inline `--settings` (only `deniedMcpServers` for its internal servers) and no `--mcp-config`.
  - It reads **everything** in the cc-home: `CLAUDE.md` (with `@import` outside the root), `env`, hooks, `permissions.allow`, skills, agents, `.claude.json:mcpServers` and `enabledPlugins`. It also gets the account's connectors and org plugins from Desktop.
  - It **inherits the chat's MCP** (`claude_desktop_config.json`), served from Desktop's shared pool. On a name clash it shows one and Desktop's wins, but the Code tab's `claude` still spawns its own copy, left idle. A fake server (`sleep`) makes the pool give up silently: test with a real MCP server or you will measure the opposite.
  - `claude_desktop_config.json` accepts **stdio only** (an `http` entry is logged «Skipped invalid MCP server config entries» and left in the file). It is **not re-read while running**: a restart is needed. Desktop rewrites the file while running (it holds `preferences`), and kept `mcpServers` written before it started.
  - Claude Code **keeps** an `mcpServers` entry written from outside while it runs (D7 = merge into `.claude.json`, never a plugin).
  - Credentials live in the Keychain as `Claude Code-credentials-<sha256(CLAUDE_CONFIG_DIR)[:8]>` (no suffix for `~/.claude`): **the name depends on the path**, so anything that moves a cc-home (`profile rename`) loses the login; the rename says so (B7). The credential Desktop's Code tab writes did not satisfy the user's CLI, which asked for `/login`.
  - `/config` inside a profile writes to `cc-home/settings.json`, which ccp generates; ccp now adopts it into the overlay on the next regeneration (B6).
  - Logs of every window, profiles included, share `~/Library/Logs/Claude`.

### `internal/supervisor` (the `ccp session` loop)

Runs `claude` as a child, watches for a usage limit, hands the session off and relaunches. Split so the dangerous part — rotating profiles at 3am with nobody watching — is auditable in one file:

- **`policy.go`** — `Chain`, the rotation state machine. **Pure**: no clock, no disk, every instant arrives as a parameter, so a 5-hour cooldown is testable in microseconds. `Next()` encodes the pendulum: *the primary if its cooldown expired* (`ReturnDue`) even when fresh loans remain, then the max-hops budget (backstop), then the first available fallback. `max_hops` counts **loans**: `Advance` does not charge a trip home and `Next`/`ReturnDue` do not let an exhausted budget block one — stranding the conversation in someone else's account with the primary free is worse than one extra relaunch, and the backstop still holds because every return must be preceded by a loan that did pay (≤ `2·max_hops + 1` launches). `ReturnDue` is also what the `return_check` timer asks. `MarkExhausted` treats a stale or zero `resets_at` as absent (a `resets_at` in the past would make a profile available the instant it was marked exhausted → ping-pong). **`DwellFor(source)` splits what `min_dwell` used to conflate**: the full value applies only to the *proactive* sensor (`"statusline"`), the one that warns before anything failed; every reactive origin — and any origin we don't recognise, because a sentinel's `Source` comes from an external payload — falls to a 30s cap (`reactiveDwellCap`). The classic justification (damping the burst of three sensors reporting one limit) is already done by `runner.fresh` and by the `if limit != nil { continue }` in the select; what `min_dwell` really buys is a floor *between* launches. Applying it in full to a reactive event held the user inside a live 429 for up to 20 minutes — `c.since` is seeded in `NewChain`, so on the first launch it was the whole value counted from the start of the run. `DwellSatisfied` (the full value) is kept for `decideReturn`, where nobody is in a hurry.
- **`detect.go`** — the sensors, all behind `Detector{Events() <-chan core.LimitEvent; Close() error}`: `NewStreamDetector` (parses `claude -p`'s stream-json *while teeing it verbatim* to the user), `NewTranscriptWatcher` (tails the `.jsonl`; never consumes a half-written line), `NewSentinelWatcher` (the StopFailure hook's sentinels, filtered by session), `NewUsageWatcher` (the only **proactive** one: statusLine sample, `.claude.json` as fallback, fires once per crossed window, and gated by `usageDatable` — the triggering window must carry a `resets_at`, because without one the Chain has no window to wait for and banishes the profile for the whole fallback cooldown on a reading that may describe an already-closed window; `core.ExhaustedAt` deliberately stays permissive because it is also what *paints* the status bar, where "95% with no date" is valid information — the rule belongs where the decision is made, not where the number is shown), and `MergeDetectors`. Contract: the goroutine is the only one that closes `events`; `Close` only closes `quit` and never blocks.
- **`launcher.go`** — process, signals and tty. The child shares the supervisor's **process group** (no `Setpgid`, no `TIOCSPGRP`): it is already the tty's foreground process, so `Ctrl-C` reaches it, and the supervisor just ignores `SIGINT` so it survives to report the result. Saves/restores `termios` (killing claude mid-TUI would otherwise leave the shell in raw mode). `BuildArgs` is pure and defers to the user: it never duplicates a `--resume`/`--session-id`/`-p`/`--output-format` the user already passed.
- **`supervisor.go`** — the loop, and the **only** place that mutates disk state. Invariant: never two children alive at once. Pre-assigns the session uuid (`--session-id`) so it knows which transcript to watch. On a limit: honour the dwell for that event's source (`Chain.DwellFor`) → `Terminate(10s)` → `MarkExhausted` → `Next` → `HandoffEndSession` if the target is home, `HandoffChain` otherwise, else park (exit 75). **The terminal outcomes are asymmetric on purpose**: exit 130 (Ctrl-C) decides by code alone, because our own SIGTERM cannot produce a 130 — but exit **0** it can, so that branch also demands `out.exited`. `Process.Terminate` returns `signaled` (did the signal actually go out) and `kill` derives `exited: !signaled`, which keeps the documented race intact (a child that prints the limit and dies in the same instant is found already dead ⇒ still its own exit) while closing the one that was systematic: a `claude` that traps SIGTERM to run its `SessionEnd` hooks and exits 0 after we killed it read as a happy ending, closed the loan and returned — the whole rotation switching itself off at the first limit with no symptom. Residual window: between the child's `exit()` and our reaper, the signal lands on a zombie and counts as ours; a genuine happy ending racing a limit event there costs one extra loan, which is the right trade. Deduplicates events by content across the whole run, because `HandoffChain` copies the `.jsonl` to the destination and the next launch would re-read the very line that caused the previous hop.
  - **The `return_check` timer** is the second reason to kill the child, and the only one nobody reports: sensors say "*this* is exhausted", never "*that other* account freed up". Its only action when it fires is `Terminate(10s)` on a **healthy** `claude` plus a relaunch in the primary — so the arming condition is a guard, not bookkeeping. `armReturnTicker(onLoan, noReturn, check)` holds it: on loan **and** the live marker's `From` is the primary (`onLoan`), `--no-return` off, `return_check > 0`. That `onLoan` guard is load-bearing: with a **degraded** loan (rotation with no transcript ⇒ no marker) there is no loan to close, and arming there would move the conversation for a reason nobody asked for. It is a separate function because arming-too-much has **no observable effect** in most states (`ReturnDue` is false at home, so an end-to-end test can't tell it apart) — the condition has to be asserted by name (`TestArmReturnTickerSoloConPrestamoVivo`). It ticks at `o.Poll` and gates on `o.Now()` so the period is the policy's (10m) while tests drive an injected clock. Firing sets `childOutcome.returnHome`, which the loop handles **before** the rotation branch and **without** `MarkExhausted` on the current profile: we left it voluntarily, it keeps its credit. The trip home itself is the same `HandoffEndSession` + new uuid + resume as the limit-driven one.
  - **`decideReturn`** is that timer's whole decision, extracted from the `select` so each rule is testable without launching anything — because this is the only move that kills a *healthy* child. In order: a already-dequeued limit yields to the pending rotation; `Chain.ReturnDue`; `DwellSatisfied`; **`sessionIdle`** (the transcript's mtime must be `return_idle` old — 90s by default; a missing transcript is **not** idle, and `return_idle: 0s` is the explicit opt-out); and finally a **non-blocking drain** of the event channel, because a `LimitEvent` the `select` had not dequeued yet would be lost when the child dies (Go picks randomly between ready channels) and the profile we leave would never reach `MarkExhausted` — it would look fresh to the next `Next()` and burn a hop on an account still in 429.
  - **Going home never creates an inverted marker.** `backHome` (`target == Primary()`) is separate from `home` (`backHome` *with a live marker*). Without that split, returning from a degraded loan fell through to `HandoffChain(loan → primary)`, which opens an ACTIVE `{From: loan, To: primary}` marker that can never be closed while at home — and the next clean exit would back-sync the conversation *towards* the loan profile, leaving the transcript where the user is not and a trace that lies about where to `--resume`. `runner.adoptHome` handles it instead: no transcript ⇒ fresh uuid in the primary (`resume=false`); transcript ⇒ `core.HandoffAdoptHome` (RewriteSession under a new uuid, **no** marker, no `archived` entry). The `returnHome` branch degrades to the same helper if it ever runs without a marker, rather than calling `HandoffEndSession` and dying with an empty `%s`.
- **`trace.go`** — presentation. The hop trace goes to `Out` (it *is* the command's output, and in headless `Out` also carries the child's stream-json); operational chatter goes to `Err`. The package does not speak i18n on purpose — `internal/cli` owns the catalog. Every movement of the conversation goes through **one** formatter, `traceMove`, whichever of the two things caused it: the budget is named the same way always (`préstamo N/M` outbound, `vuelta a casa, no gasta préstamo: siguen N/M` home), the trip home is never called a *préstamo*, and because it doesn't charge budget the repeated number is explained in the line instead of left dangling. Sharing the formatter is the point — two entry points printing the same event two ways is exactly the bug `trace_test.go` now pins.

### `internal/cli` & `internal/tui`

`internal/cli` is dispatch + text/JSON formatting only. `internal/tui` is a bubbletea+huh app (3 panels: Profiles | Rules | Status) launched when `ccp` runs with **no args and a TTY**; with no TTY it falls to the CLI (never blocks scripting). The TUI only calls `internal/core` — every action has a CLI equivalent. **Anything drawn on `/dev/tty` must repoint lipgloss's default renderer at that file** (`openTTY` does it): the default renderer probes `os.Stdout`, and on the real `ccp handoff` path that stdout is the shell function's command substitution — a pipe — so termenv resolves "no colour" and every style silently becomes dead code that still tests green (tests have no tty either). `NO_COLOR` keeps working; termenv reads it from the environment.

`internal/tui/shell.go` es el **único** sitio que pinta chrome: cabecera, cajas,
cursor, ventana, línea de estado y pie. Una vista construye un `viewSpec` (unos
`panelSpec` con sus `rowSpec`) y llama a `renderView`; alinear columnas sigue
siendo de la vista, pero el `▸`, el recorte y la caja no. Antes había tres
renderizadores a mano repitiendo la idea, que es el mismo bug que `traceMove`
evita en el supervisor. `panelSpec.MaxRows` es lo que permite pintar un
`permissions.allow` de 200 entradas sin viewport: una ventana alrededor del
cursor con marcas `↑ N más` / `↓ N más`.

`e` sobre un perfil abre la **vista de perfil** (`modeProfile`,
`profile_view.go`): tres cajas —Instrucciones · Env · Efectivo— sobre
`core.ProfileEffective`, que devuelve la procedencia como dato (`OriginGlobal` /
`OriginOverlay` / `OriginAuto` / `OriginClaudeJSON`, más `Shadowed` cuando otra
capa traía la misma clave). Desde la Fase 0 (B5) trae también `EffMCP` (los
`mcpServers` del `.claude.json` que lee el perfil), `EffDeny`, `EffAsk` y
`EffSettings` (`model`, `outputStyle`, `permissions.defaultMode`,
`statusLine.command`, este último con el envoltorio de los sensores si están
instalados). Van **al final** de `Sections` para no mover a nadie; la TUI y la
GUI los ordenan a su gusto (`effGroups`, `EFFECTIVE_ORDER`). Los MCP no tienen
archivo editable: su `.claude.json` lo reescribe Claude Code, así que `e` ahí
explica dónde viven en vez de abrir el overlay. Se edita lo que `core` ya sabe escribir: reglas por `InstructRuleAdd/Rm`,
variables por `OverlayEnvSet/Del`, hooks por `InstructAdd` (con el `ActiveProfile`
del `InstructCtx` fijado al perfil MIRADO, no al de la terminal). Los hooks se
añaden pero **no** se borran — viven en arrays sin id estable— y la tecla lo dice
en vez de fingir. El CLI no cambia: `ccp profile config <perfil>` sigue abriendo
el editor.

### Layers and projection (`core/mcp_layers.go`, `core/mcp_project.go`, `core/profile_artifacts.go`, `core/settings_layers.go`, `core/projection_check.go`, `core/doctor_projection.go`)

Spec §6, [ADR 0011](docs/adr/0011-una-fuente-declarada-varias-proyecciones.md), measured on [0016](docs/adr/0016-what-desktop-reads-from-a-profile.md). The user **declares** in layers; ccp **projects** into the files the apps actually read, and everything projected is derived.

- **`mcp_layers.go`** — the layers: global = `~/.claude.json:mcpServers` (`src + ".json"`), profile = `overlay/mcp.json` with the shape of `.mcp.json`, project = `<repo>/.mcp.json` (read by Claude Code on cwd; ccp never projects it). What only ccp cares about — `targets` per server, `disabled` per profile, `desktop_default` — lives in the `mcp:` block of `ccp.yaml`, additive like `auto_handoff` (schema stays `2`, `MCPConfig.Extra` + `stripMCPKnownKeys`). `MCPEffective` = global ⊕ profile − disabled, profile wins a clash, sorted by name. A missing layer file is an empty layer; an invalid one is an error with its path, because whoever regenerates cannot project blind.
- **`mcp_project.go`** — the two projections, and one rule underneath both: **ccp only touches the entries whose name it registered as its own** (`cc-home/.ccp-managed.json`, `<data-dir>/.ccp-managed-mcp.json`). A declared name that was already there by hand is a `Conflicts` row, never an overwrite. That registry is derived: `reconcileManaged` rebuilds it by taking as managed any declared name whose value in the destination already equals the declared one, and it is never captured by snapshots or backups.
  - **CLI** (`ProjectMCPToCLI`) merges into `cc-home/.claude.json` — technique A, D7, validated by M6: Claude Code keeps what is written from outside. Every other key survives; the write is tmp+rename keeping the mode. `default` returns early: its destination **is** the global layer.
  - **Desktop chat** (`ProjectMCPToDesktop`) writes `profiles/<n>/desktop/claude_desktop_config.json`, keeping `preferences` and every unknown key. Two limits come from 0016 and are load-bearing: **stdio only** (an `http`/`sse` entry is discarded by Desktop at start-up, so it is reported in `RemoteSkipped` instead of written) and **never while the window runs** (it is not re-read hot, and Desktop rewrites the file from its in-memory copy) — the projection is left pending in `state/desktop-pending.json` and applied on the next launch. `core` does not run `ps`: `internal/cli` injects the probe through `SetDesktopRunningProbe`.
  - `Check*` is **the same function with `dry=true`**, not a parallel comparator — a diff written apart ends up answering something else than the write, the bug `traceMove` avoids in the supervisor.
- **`profile_artifacts.go`** — `ProjectProfileArtifacts` mirrors `overlay/{agents,commands,skills,output-styles}/` into the cc-home with `mirrorTree` (real directories, symlinks only at the file leaves — the shape Desktop demands), overlay first and global second, so precedence falls out of `mirrorTree` never overwriting an existing entry. **`seedCCHome` does not change**: the bash oracle asserts directory symlinks right after `profile add`, and that stays true until the profile declares something of its own; the conversion happens on first use. A directory the profile does not declare is left alone.
- **`settings_layers.go`** — `SettingsLayerGet/Set(home, src, layer, path, value, del)` edits one key of one layer (`global` = `~/.claude/settings.json`, `profile:<n>` = the overlay), atomically, keeping the mode and following a symlink. Hooks are edited as the **whole array of an event**, which is what fixes "they get added but never removed". `applyPermissionUnion` is the opt-in union: the merge still **replaces** arrays (ADR 0002), unless the overlay says `"permissions": {"$merge": "union", …}`, and then allow/deny/ask come out global ⊎ overlay, deduped, global first. The mark is an instruction to ccp, never reaches the generated `settings.json`.
- **The projection runs in every regeneration.** `CfgRegenerateReport` calls `ProjectProfileArtifacts` + `projectProfileMCP` after merging settings, for the same reason the `/config` drift adoption lives there: if only `profile sync` projected, every other path (an `instruct add`, a restore, a rename) would leave the destination stale. A projection error does not bring the regeneration down — the cc-home is already written — it is reported in `SettingsDrift.MCPErr`.
- **`projection_check.go` / `doctor_projection.go`** — `ProfileProjectionCheck` powers `ccp profile sync --check` (exit 1 when stale) and serve's `profiles.drift`. `Stale()` counts what a sync would **fix** (writes, removals, unmirrored artifacts, the deferred write); conflicts and what the chat cannot load are **not** stale — they are permanent states the user decides, and counting them would pin the check at 1 forever. The doctor codes are `projection_stale`, `desktop_restart_pending`, `mcp_command_missing`, `mcp_unmanaged_only_desktop` and `cc_home_symlink_nonleaf`; 0009's rule applies here too — a source that cannot be read produces silence or an error, never a green row. `EffRow.AppliesTo` (`cli`, `desktop-code`, `desktop-chat`) is filled at the end of `ProfileEffective`, so no section has to remember; only the MCP section sets it per row.

### Inventory and adoption (`core/inventory*.go`, `core/adopt.go`)

`ccp scan` / `ccp adopt` (spec §5, Fase A). `BuildInventory(InventoryRoots)` is read-only with **injected roots** (HOME, CCP_HOME, the global source, the default Desktop data dir, the managed dir, rc files, `LookPath`): it never reads the environment itself, so a whole fake machine fits in a test. Rules: a source that exists but can't be read is `unknown`, **never** empty; secret values never leave it (only `Secrets` paths; `SecretHash` is `json:"-"` and exists only so `AdoptPlan` can tell two copies of an MCP with different tokens apart); `AppliesTo` follows ADR 0016 (cc-home and global → CLI + Code; `claude_desktop_config.json` → chat + Code, stdio only). `AdoptPlan(inv, AdoptInputs)` is pure (`AdoptInputsFor` reads logins, keys and launchers from disk) and emits steps with **stable, unique IDs** (hash of kind+from+to+key+items: kind+from+to alone collided for every MCP of one file, and `--only` applied them all). An MCP only in Desktop is lifted to `~/.claude.json` if it is in the default window or in every window, **never** when copies differ in shape or secrets (global projects to every profile). `AdoptApply` needs `Before` (the safety snapshot) to succeed first; `Only` nil = defaults, empty non-nil = nothing (the GUI with nothing checked applies nothing). Adopting a `~/.claude-x` copies config into a new profile's overlay (never tokens, never `env`) and leaves the original alone.

### The config editor (`core/config_items.go`, `core/config_edit.go`, `core/mcp_crud.go`)

Spec §7, Fase C. One engine behind both faces of the unified editor — P-20 in the GUI and `ccp mcp` in the terminal — so «what is here» and «what gets written where» have a single definition.

- **`config_items.go`** — `ConfigItems(r InventoryRoots, layer ConfigLayer)` lists what a layer (`global` · `profile:<n>` · `project:<path>` · `desktop:<n>`) has to edit, by type (`CfgType*`, the screen's left column), each row with its provenance (`InvScope`), its `AppliesTo`, and a `Why` when it is visible but not editable. It does **not** walk the disk a second time: it starts from `BuildInventory`, which already reads every source under the doctor's rule (unreadable is `unknown`, never «empty»), and adds the three things the inventory cannot know, because its question is a different one:
  - the **write address** (`ConfigRef`), which is not always where the item was found — a profile's MCP servers are declared in `overlay/mcp.json` and **projected** into the cc-home and the window (§6.1), so what is projected is shown but not editable (editing it there would be eaten by the next `profile sync` without a word) and its copy is not repeated as a second row;
  - what a profile declares in its own overlay (`mcp.json`, `agents/commands/skills/output-styles`), which is the projection's source and not Claude Code's config;
  - that **`default` has no layer of its own**: its `CLAUDE_CONFIG_DIR` is `~/.claude`, so the global is what is read and written, and the reference says so.
  - `CfgTypeSettings` is not in the design and exists because the remaining `settings.json` keys (`model`, `keybindings`…) are editable and had to land somewhere: without it the very keys the user touches with `/config` would vanish from the screen.
- **`config_edit.go`** — `ConfigItemGet/Put/Delete` route to the writer that already existed (`SettingsLayerSet`, `OverlayEnvSet/Del` — which validates and regenerates —, `jsonFileSet` for the files that belong to no settings layer, artifact files as they are), and **regeneration is decided in one place** (`cfgRegenTargets`, through `cfgAfterWrite`): the global reaches every profile, an overlay only its own, a project or a window generate nothing. Creating a file the layer does not read (a loose hook in a profile's overlay) is refused (`cfgFileTypeInLayer`) instead of written where nobody would ever read it. `ConfigWrite` reports the file, who was regenerated and the projections of that regeneration (`MCP`/`MCPErr`).
- **`mcp_crud.go`** — `MCPPut`/`MCPDelete` write in the layer that **declares** (global `~/.claude.json`, profile `overlay/mcp.json`, project `.mcp.json`) and in no other: a Desktop window is a projection target, so writing there is refused, saying where it goes. They route through `ConfigItemPut/Delete` rather than touching the file, so the map of «what is written where» stays in one place. On top of that writer: `ValidateMCPServer` (stdio with `command`/`args`/`env`, or remote `http|sse` with `url`/`headers`, never mixed) runs **before** writing, because a malformed entry breaks nothing visible — Claude Code discards it and carries on — so this is the only moment anyone can say what is wrong; without `type`, the transport is deduced with `mcpKind`, the same one the projection uses, or ccp would reject what it projects itself. A secret in the clear is refused in the **project** layer (the `.mcp.json` travels in the repo; the way out is `${VARIABLE}`, and `${VAR:-value}` does not count) and kept in the profile's, which only travels in backups *with* secrets and sealed inside snapshots. And the layer must exist, because the writer creates missing directories: a typo'd profile used to take its server to a `profiles/<typo>/overlay` nobody would read.
- `MCPSetTargets`/`MCPSetEnabled` touch the `mcp:` block of `ccp.yaml` (Load → mutate → Save) and regenerate what they leave stale: every profile if the targets change, only its own for a disable. Declaring both targets deletes the entry, since with no entry both already apply. Disabling in `default` is refused: its layer **is** the global, and there is no projection to turn off.
- `ConfigWrite.RestartPending()` is the «pending restart» notice both front-ends print: the profiles whose window got a deferred projection, which keeps the previous MCP servers until it is relaunched (ADR 0016).
- Fronts: `internal/cli/mcp.go` (`ccp mcp list|add|rm|enable|disable|targets`, `--scope` defaulting to the terminal's **active profile** — whoever types this is already inside one — and `--json` everywhere; not in the completion, which is golden contract) and `internal/cli/serve_config.go` for the GUI. `ccp mcp list` also prints what the profile **receives** without it being in its cc-home (`mcpUnprojectedRows`): what is disabled and what only goes to the chat, or a `disable` would make a server vanish from the only list it can be re-enabled from.

### Snapshots (`internal/snapshot`, `internal/vault`, `core/snapshot_*.go`)

`ccp snapshot` is the history of the **whole** configuration ([ADR 0012](docs/adr/0012-snapshots-content-addressed.md), spec `2026-09-18-config-unificada-snapshots-nube` §8). Three layers, and the split is the point:

- **`internal/vault`** — `Seal`/`Open` (XChaCha20-Poly1305, fresh nonce each time) and `DeriveKey` (Argon2id with bounded params, so a hostile `.ccpsnap` can't ask for 64 GiB of RAM). Nothing else.
- **`internal/snapshot`** — the format and the store, and it **never imports `core`**: the cloud backend will share it and knows nothing about `~/.claude`. Blobs are content-addressed (`objects/ab/cdef…`, `CCPB1` header + a flag byte: plain or sealed with `store.key`, the hash as associated data, so a sealed blob can't be swapped for another). `GetBlob` re-hashes what it returns. A manifest's id is the sha256 of its canonical JSON **without** `id`/`label`/`pinned` (pinning or labelling doesn't change it; editing anything else makes it fail to load). Manifest filenames carry nanoseconds, because two snapshots in the same second used to sort at random and `latest` picked either. `Capture` returns `ErrNoChanges` (with the latest manifest) when nothing changed; `Prune` is restic-style with a 1h grace for blobs a concurrent capture may have just written; `Export`/`Import` move one snapshot as a `.ccpsnap` (tar.gz), where secrets travel only re-sealed with a passphrase and imported objects are verified against their hash.
- **`core/snapshot_layout.go`** (what is captured, and the logical paths) and **`core/snapshot_restore.go`** (where each logical path goes back). They are the only map between logical paths and disk. Rules that don't bend:
  - **A logical path writes only to its closed list of destinations** (`snapshotTarget`): they also arrive from foreign `.ccpsnap` files, so `..`, unknown prefixes, a project file outside `projectLocalFiles` or a project `path` that isn't absolute are all refused.
  - **No restore without a pre-snapshot** (`pre-restore`), and a `ccp.yaml` with a newer schema aborts at **plan** time, before that snapshot, so a refused restore leaves no trace. `ccp.yaml` is written first and under its lock, then `seedCCHome` + `CfgRegenerate` for the touched profiles (all of them if anything under `claude/` changed). Nothing that exists only on disk is deleted.
  - **From a `.claude.json` only the configuration travels** (`ClaudeJSONConfig`: `mcpServers`, and per project `mcpServers`/`enabledMcpjsonServers`/`disabledMcpjsonServers`/`allowedTools`), classed `secret`, and restoring **merges** it (`ClaudeJSONApplyConfig`): tokens, `machineID` and counters belong to the machine.
  - Symlinks are never followed on capture (`seedCCHome`'s links point at things captured under their own path). Projects are those with a rule, keyed by their normalised git remote so the same repo elsewhere is the same project; a project whose folder is gone is skipped as `project_missing`.
- **CLI (`internal/cli/snapshot.go`)**: `restore` without `--yes` prints the plan and exits **1** (`--dry-run` exits 0). Automatic snapshots: `withSafetySnapshot` before `profile rm` and `backup restore` (and `autoSnapshot` in the matching `serve` methods) is **blocking** — if it can't be saved, the operation doesn't run. `maybeDailySnapshot` runs from `Dispatch` only for the commands in `dailySnapshotCmds`, is best-effort (never fails, never prints) and keeps a `.daily-check` marker so a day without changes doesn't re-hash everything on every command. `CCP_NO_AUTO_SNAPSHOT=1` turns both off, and `internal/cli`'s `TestMain` sets it so the rest of the suite behaves as before.
- **GUI (`gui/src/screens/Snapshots.tsx`, P-17)**: the same engine through the `snapshot.*` serve methods. Restoring is two calls on purpose — `dry_run` for the plan, a second one to apply — so the screen cannot write by being looked at, exactly as the CLI's missing `--yes` makes a restore a plan. The checkboxes ARE the `--only` prefixes (`groupOf` cuts at the first segment, or the second for `desktop/` and `project/`), so the CLI line it offers to copy does what the button does. `snapSummary` carries `bytes` (the sum of the items' sizes) because the timeline needs a size per row without loading a manifest each; it is what a snapshot *captures*, not what it occupies, and the screen says so — the blobs are shared.

### `ccp serve` & the desktop app (`gui/`)

`ccp serve --stdio` is the engine as a machine API: NDJSON over stdin/stdout, protocol `1`, a `{"event":"ready"}` line first, one `{"id","result"|"error"}` per request (`internal/cli/serve.go`; methods in `serve_methods.go` / `serve_ops.go`, one `serveRegistry` map). Rules that keep it honest: **reads run concurrently, writes are serialized** by `server.writeMu` (several are read-modify-write of `ccp.yaml` that the `Save` flock doesn't cover whole); **stdout is the protocol**, so `cmdServe` points `os.Stdout` at stderr and anything that prints stray goes to the GUI's log instead of into a response; commands that already exist are reused through `runInProcess` (same `Dispatch`, output captured), never re-implemented; and `CCP_SENSOR_BIN` makes the sensors point at the *installed* ccp when the GUI runs its bundled copy. New engine ops it needed live in `core/gui_edit.go` (`ProfileUpdate`, `AutoSetEnabled`, `AutoAllowReplace`, `AutoPolicySet`) and `core/conversations.go` (every profile's sessions, terminal + Desktop, with titles). Adding a method doesn't bump the protocol; changing the shape of an existing message does. `profiles.sync` returns `drift` (always an array, one row per profile with something to report, each list an array too — each row now also carries `mcp`/`mcp_error`, what the projection did) and `profiles.rename` returns `relogin`, both next to `"ok": true` — a field added, not a shape changed. The P-20 editor lives in `serve_config.go` (`config.items`, `config.item.get|put|delete`, `mcp.list|put|delete|setTargets|disable`): the layer always arrives in the params, because serve has no terminal to take an active profile from and guessing would write somewhere other than what the user is looking at; every write answers with core's `ConfigWrite` plus `restart_pending` (the method `RestartPending`, which would not travel in JSON). `config.effective` is registered onto `srvProfilesEffective` — the screen's name for a result that already existed, not a second implementation. `profiles.drift` is `ccp profile sync --check` for the GUI: it goes through `r()` (read) because it writes nothing, and each row carries `stale` straight from `ProjectionCheck.Stale()` — the GUI must not recompute it by summing lists, which is how two front-ends drift apart over the same data.

`gui/` is Tauri 2 (Rust) + React/TypeScript, built from `docs/ui-design/ccp Interfaz - standalone.html` (18 screens, P-01 … P-18; P-19 and P-20 came later and have no page in that file). **Rust is only a bridge** (`src-tauri/src/bridge.rs`): it picks the binary (`CCP_GUI_BIN` → `CCP_SANDBOX` → installed ccp if it speaks `serve` → the bundled sidecar), strips `CCP_PROFILE`/`ANTHROPIC_*`/… from the child's env (the GUI passes context explicitly on every call) and gives it the login shell's `PATH`. What needs a terminal (`/login`, `ccp handoff`, `ccp session`) is **never faked**: the UI explains it and `native.rs` opens Terminal with the command typed, accepting only `ccp` argv, each argument quoted. Every screen shows its CLI equivalent. UI strings are Spanish inside `t('…')`, English in `gui/src/lib/i18n_en.ts`. Develop against the sandbox (`npm run sandbox` → `gui/.sandbox`, its own HOME and CCP_HOME) — never against the real `~/.config/ccp`. Checks: `npm run typecheck`, `cargo test && cargo clippy --all-targets && cargo fmt --check` in `gui/src-tauri`. Details in `gui/README.md`.

**P-20 Configuración** (`screens/Configuracion.tsx` + its MCP table and effective view, editors in `lib/config_edit.ts`) is the unified editor: layer on top (global · profile · project · desktop window), types on the left, items in the middle with their provenance and their *where it applies* badges. It absorbs P-05 — which stays reachable from the profile detail, because it still owns the env/instruction editors that screen links to — and the managed-only view of P-15. It writes only through `config.item.*` and `mcp.*`, so the barriers are core's: MCP secrets are **masked** in the form and whatever the user leaves masked is restored on save; a layer action («llevar a…») is the same item with another layer, so core picks the file and there is no new route per destination. Every write reports where it landed, who it regenerated and which Desktop window keeps the previous MCP servers until it restarts — the projection is done by the write itself, not by a second call.

**P-17 Snapshots** (`screens/Snapshots.tsx`) is what the design file's «Copias» grew into, and it is reached from Ajustes like the old one (`Copias` still lives in `screens/Ajustes.tsx`, one row below): timeline, what each snapshot captures, diff against another snapshot or against the live state, restore, prune, pin, label, export and import, all over the `snapshot.*` methods. The two rules it must not lose are in the snapshots section above: restoring is **two calls** (plan, then apply) and the checkboxes are the `--only` prefixes. `ccp backup`'s `.tar.gz` stays in Ajustes, which is where it belongs now — it is the old format, for moving a configuration to another machine by hand.

### Config & state locations (`~/.config/ccp`)

- **`ccp.yaml`** — the single source of truth (replaces `profiles.tsv` + `rules.tsv` + `config` + per-profile `meta` + global/profile `authored.tsv`). Schema `version: 2`. `default` is implicit (never serialized). No inheritance: deepseek profiles store their 4 fields explicitly; `defaults` only seeds new ones.
- **`auto_handoff:` (in `ccp.yaml`)** — the auto-rotation policy. `enabled` (master switch for `ccp session`), `policies.<name>` (`fallback` = the loans *in order*, primary implicit; `threshold` %, `min_dwell`, `max_hops`, `return_check`, `return_idle`, `cooldown.{strategy,fallback}`), `allow_from` (the compliance gate, see `auto.go` above) and `hooks` (the list of profiles whose `settings.json` carries the sensor layer — the source of truth for that, **not** the generated file). Additive: `version` stays at `2`, so an older binary round-trips the block through `Config.Extra`. That top-level catch-all protects the **key**, not its **contents**: `AutoHandoff` and `AutoPolicy` carry their own `Extra map[string]any` with `yaml:",inline"` so an unknown key *inside* the block survives too. It needs `stripAutoKnownKeys` (store.go) as its partner, because goccy's inline map captures every key of the node, typed ones included, and leaving them there would serialise them twice — the same reason `knownTopKeys` exists.
- `handoffs.yaml` markers gained `auto: true` (created by the supervisor) and `hops: [...]` (the trail of destination profiles). Both `omitempty`, `HandoffsVersion` still `2`.
- `state/auto/rate-limits/<profile>.json` — the last statusLine sample (`used_percentage` + `resets_at` per window, plus when it was taken). `state/auto/sentinels/*.json` — what `ccp _limit-hook` leaves for the supervisor to pick up. Both are caches: deleting them costs detection quality, never correctness.
- **`mcp:` (in `ccp.yaml`)** — ccp's own metadata about the MCP layers: `targets` per server (default `[cli, desktop]`), `disabled` per profile (a profile turning an inherited server off without deleting it) and `desktop_default` (reserved: the `default` window is only inventoried, D8). Additive exactly like `auto_handoff`, with its own inline `Extra` and `stripMCPKnownKeys`.
- `profiles/<name>/cc-home/.ccp-managed.json` and `profiles/<name>/desktop/.ccp-managed-mcp.json` — the names ccp wrote into each destination. Derived: losing one only means those entries look foreign until `reconcileManaged` matches them by content.
- `profiles/<name>/api_key` — provider key, `chmod 600`, **never** in `ccp.yaml`, rc, or git.
- `profiles/<name>/cc-home/` — every non-`default` profile's `CLAUDE_CONFIG_DIR`. `CLAUDE.md`/`settings.json` are generated (not symlinked). `ccp profile login <name>` once per official profile.
- `profiles/<name>/overlay/` — the profile's own config (`CLAUDE.md` + `settings.overlay.json`), a lowest-precedence baseline; a repo's `.claude/settings.json` wins. Since Fase B it also holds the profile's declared layers: `mcp.json` (the shape of `.mcp.json`; captured as `secret` in snapshots because it carries `env`/`headers`) and `agents/ commands/ skills/ output-styles/`, which every regeneration projects into the cc-home.
- `profiles/<name>/state/` — derived state that is not Claude Code's: `last-settings.json` + `last-overlay.json` (baseline for the `/config` drift), `drift-pending.json` (drift nobody has shown yet), and the `0600` copies `settings.invalid-<hash>.json` / `settings.rescued-<hash>.json` (last 20 of each), plus `desktop-pending.json` (the chat projection waiting for that window to restart). Never captured by snapshots or backups; deleting it only turns adoption off until the next regeneration.
- `snapshots/` — the snapshot store: `store.key` (`0600`, seals the `secret` blobs; losing it loses the secrets of every local snapshot, the rest stays readable), `objects/`, `snaps/` and `.daily-check`. Backed up by nothing but itself — `ccp snapshot export` is how it leaves the machine.
- `install-source` — repo path for `ccp upgrade`. `.claude/ccp-authored.tsv` (project-scope authored) stays versioned per-repo (ccp never rewrites the user's repo files).

### Distribution

`install.sh` is **Go-aware**: detects OS/arch → downloads the prebuilt release binary and verifies its `sha256` against `checksums.txt`, falling back to `go build` if there's no release but a Go toolchain. It removes the old bash libs (`~/.local/lib/ccp`), re-points `install-source`, and copies `commands/ccp/*.md`. It also runs **standalone** — `curl -fsSL https://raw.githubusercontent.com/JoseAFlores777/ccp/main/install.sh | bash` — which is the documented way to install. In a pipe there is no `BASH_SOURCE`, so the checkout is detected by **content** (`is_checkout`: `install.sh` + `cmd/ccp/main.go`), never by `$0`; with no checkout the script bootstraps one into `$CCP_HOME/src` (`git clone --depth 1`, tarball fallback via `codeload`, `CCP_SRC_DIR` to move it, `CCP_NO_SOURCE=1` to skip it) so the `/ccp:` commands and `install-source` still have a source. Bootstrapping is **never fatal**: if it fails the binary still installs and the script warns that `ccp upgrade` has no registered source. Never write `"$VAR…"` in that script — bash reading from **stdin** in a UTF-8 locale swallows the `…` into the variable name and dies with *unbound variable*; brace it (`${VAR}…`). `.github/workflows/release.yml` builds the 4-platform matrix (darwin/linux × amd64/arm64) + checksums on each `v*` tag. `ccp upgrade` re-runs `install.sh` then `profile sync` with the new binary. **Go is not installed on the user's machine → the prebuilt-release path is the effective one.**

## Conventions

- Dispatch is by hand in `internal/cli`. Internal/scripting commands: `_resolve`/`resolve`, `_env`, `_hook`, `completion-shellinit`. Migration fires lazily (`ensureMigrated`) at the top of config-touching commands.
- Output helpers respect `NO_COLOR` and non-TTY (`internal/cli/present.go`). Keep user-facing text Spanish.
- The shell function / hook / completion text lives as **byte-identical string constants** in `core/shellinit.go`. `ccp uninstall` strips the block by the `# >>> ccp shell init >>>` / `# <<<` markers; don't change those markers casually. If you change the shell tail, update the bash oracle in `legacy/` and regenerate the golden too.
- **macOS portability**: Go is portable; `install.sh` stays POSIX-ish bash with no GNU-only coreutils (checksum via `sha256sum` *or* `shasum -a 256`).
- Machine-readable surface (keep stable): `ccp resolve [path]` and `ccp path test [path]` print the profile name and set exit codes (0=non-default, 1=default); `ccp profile sync --check [<name>]` exits 1 when a profile's projection is stale and 0 when everything is in place, so it works as a guard in a script; `ccp status --json` emits `active`/`profile`/`profile_type`/`cwd`/`repo`; `ccp auto status --json` emits `enabled`/`cwd`/`policy`/`primary`/`fallback`/`denied`/`sensors` (+ `error` when the policy doesn't resolve — the JSON stays valid and the exit code is 1), with `fallback`/`denied`/`sensors` always arrays, never `null`. `ccp desktop list --json` emits `profile`/`data_dir`/`exists`/`bytes`/`app`/`color` (`app`/`color` are empty strings without a launcher) and is always an array (`default` is always the first row, with an empty `data_dir`). `ccp desktop sessions --json` emits `profile`/`uuid`/`title`/`cwd`/`last_activity` (RFC3339, `""` when Desktop didn't record it)/`archived`/`transcript`, only sessions with a local transcript, always an array. `ccp mcp list --json` emits `scope` (the layer in `--scope` syntax)/`name`/`type`/`detail`/`source`/`targets`/`applies_to`/`editable` (+ `disabled`/`why`/`missing`), always an array; `ccp mcp targets --json` emits `name`/`targets`/`declared`, also always an array.
- The two internal sensors (`ccp _statusline`, `ccp _limit-hook`) must **always exit 0** and never fail loudly: a statusLine that breaks leaves Claude Code without a status bar, and a hook that fails nags the user on every turn. `_statusline` also deliberately skips `ensureMigrated` — it runs several times a minute from inside CC, and migrating the user's config from a sensor would be mutating state nobody asked to mutate.
- The auto layer writes the **absolute** path of the running binary (`os.Executable`) into each profile's `settings.json`. Moving the binary without re-running `ccp upgrade` / `ccp auto install` / `ccp profile sync` leaves the sensors pointing at the old path.
- `snapshot` and `mcp` are **not** in the completion, like `backup` and `serve`: the completion text is golden contract, and adding a command there means updating the bash oracle and regenerating the golden.
- **Never commit without explicit user authorization in the current turn**, and never add `Co-Authored-By` trailers (see the user's global instructions).
